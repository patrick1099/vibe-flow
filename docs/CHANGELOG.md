当前需求区，压缩后以磁盘上的约定为意图源，不能因为代码里没有就删掉未实现的要求；仍要遵守的"不做什么"进当前规格，
不只进 CHANGELOG。没选的路：新建 DECISIONS.md（用户已嫌文档多；HANDOFF 本来就管"做到一半"这段）；并进 NEEDS.md
（它只在好档有，也不管做法）；改 ai-room 让台账记结论（那是另一个工具的事，由这里的"审完记一条"覆盖）。

0.17.1（2026-10-06）文档闸认 worktree。起因是用户看到一次误报问"为什么报错"：protocol-simulator 的代码和
BLUEPRINT/CHANGELOG 都在 `.worktrees/rederive/` 里改了，同一轮合并回主仓、删掉 worktree，闸却报文档没动。根因：
worktree 删掉后，对话记录里的路径全都不存在，往上找项目落到了主仓，却拿主仓文档去比 worktree 里写过的文档；
0.15.0 起改看修改时间也躲不过，删掉的代码按最近一层还在的目录（`.worktrees`）算时刻，那正是删 worktree 的时刻，
晚于合并写回的文档。用户的个人仓规矩是"一律先开 worktree 再改"，所以每次都会撞上。改成：已删 worktree
（`.worktrees/<名>/`、`.claude/worktrees/<名>/`）里的代码换成主仓同一相对路径，按合并写回的修改时间判，放宽 5 秒；
worktree 里改过的文档随同一次合并写回，落在窗口内；没改的文档还是旧时刻，照样拦。worktree 还在时它本身就是带
docs/ 的完整副本，照旧按它判。没选的路：查 git 看分支是否已合并（要找出是哪个分支、合并到哪，绕得远，修改时间已经够）；
worktree 的路径一律换成主仓（worktree 还没合并时，主仓文档确实没变，会误拦）。已知盲区：worktree 没合并就删掉
（放弃了）时，按主仓旧文件判，结果不可靠，但这时本来也没有要记的改动。

0.18.0（2026-10-06）压缩后读回和文档闸不再只按会话目录找项目。起因是用户让宏观复查前几天的改动"到底有没有
优化流程、解决我担心的问题"：翻真实记录发现，9-30 以来十几个会话全是从公司仓目录启动、用绝对路径改个人项目的，
而 0.17.0 的读回只从会话目录往上找 HANDOFF，个人项目的「已谈定」压缩后一次也没注入过（当时的验收在临时目录里跑，
没暴露）；文档闸对 shell / python / esafe-code 落盘的补扫也只扫会话目录所在仓库，加密环境下改个人仓正好走这条路。
改成：从对话记录里取本会话实际碰过的路径分级——读或写过 HANDOFF / NEEDS、Write / Edit / esafe-code 写过、本会话为它
开过 worktree 的项目，加会话目录，注入「已谈定」全文，最近在做的排前（最多 3 个）；只读过或只在命令里提到的项目只列
路径，当前任务属于它们才去读。文档闸补扫本轮写过或命令里写出路径的仓库（最多 6 个）。个人仓规矩是 worktree 放仓库
外、合并后删掉，对话里的路径因此全部失效，改为从成功执行的 `git worktree add` 解析"worktree → 主仓"换回主仓路径，
文档闸也按它判已合并的 worktree。顺带给文档闸判项目根加了进程内缓存，长回合从约 4 秒降到 2 秒。codex 审了四轮：
方案阶段要求按可信度分级、只读项目不注入、要认 shell 写入；实现后挑出 cd 的选项被当成目录、失败的 worktree add 覆盖
正确映射、最近优先按写入时刻排会把回头接着做的项目挤掉、esafe-code 命令里所有路径都被当成写入、shell 里提到 HANDOFF
就注入、按修改时间推断写入会误升只读路径、`echo git worktree add` 被当成执行过，均已改。没选的路：按命名猜 worktree
属于哪个主仓（`-wt-x`、`~/worktrees/x`、`~/wt/x` 各种都有，猜错会把别的项目的约定套过来）；按修改时间推断 python
落盘（worktree 删后查不到，碰巧被别处改过又会把只读路径误升为写入）；把只读过的项目也注入（读过不等于在做）。已知
局限：不开 worktree、只用 python 落盘的项目只列路径不注入；命令里提到的别的仓库若有别的会话同时在改，文档闸可能
多拦一次；Codex 侧文档闸只多扫补丁所涉仓库，shell 命令里的路径还没接，压缩后读回 Codex 侧仍未接。

0.20.0（2026-10-06）文档闸加「这批不用记」回执。起因是宏观复查翻真实记录：AI 被闸拦下、说明"这批不用记"放行后，
后台任务完成把它唤醒（那不是人类消息，本轮范围不变，`stop_hook_active` 也已复位），同一批改动被原样再拦一遍，
唤醒几次拦几次——用户最早的担心正是维护文档这件事"占用上下文空间，导致ai做事降智"，重复提醒只会加重它。改成：
AI 判断不用记时，跑闸提示里给出的回执命令写一条结构化回执（哪对文档 + 代码指纹 + 一句理由），之后同一状态不再提醒；
fork 回来说"这批不用记"、文档没动时，主 agent 同样写回执。codex 先后审了两轮，采纳的：回执由 AI 显式写，不解析回复措辞；
指纹绑定实际文件内容、路径和删除状态，不用不含 HEAD 的 `code_state` 哈希；按 worktree 隔离；缺文档另判，不能被回执豁免；
session-sweep 的文档探测也要认；键用那对 BLUEPRINT/CHANGELOG 而不是项目根；指纹同时绑定这两份文档的内容，防止代码
退回旧状态时旧回执复活；待判定的代码不在快照里、或快照拿不全时一律不豁免；每对文档一个文件原子替换，防并发覆盖。
否决的：去掉 `stop_hook_active` 放行——去掉后 AI 被拦既不写回执也不派 fork 时会无限循环；它只防循环，去重靠回执。
没选的路：按传入判定函数的路径集合算指纹（session-sweep 只传每个目录最新的一个文件，两边永远对不上）；按项目根当键
（同目录几个旁挂脚本会互相豁免）；回执放进项目仓库或 `.git` 目录（前者污染仓库，非 git 项目没有后者）；解析 AI 回复里
"不用记"之类的措辞。已知局限：被 gitignore 的代码、超过 3000 个文件的项目，回执验证不了，照常提醒；session-sweep
先按目录只留最新一个文件，可能留下的是 AGENTS.md 而把同目录代码丢掉，这是它原有的漏报，不在本次范围。
