# clarify-needs 设计（把 reality-check 改造成需求分析 skill）

日期：2026-07-15
状态：设计已确认；**结构定稿见 §十六（薄核 + 厚兜底），它覆盖 §四–§十的"操作分层"**；SKILL.md 薄核 + references/deep-needs-analysis.md 厚版已写、待 GREEN 验收。
读法提醒：§四–§十三是**内容源**（角色/分级/劝退/防漏/理论一字不少），但它们的**运行定位以 §十六 为准**——默认路径只走薄核，这套机制按触发门进厚版，不是每次全走。

## 一、为什么做这个

vibe coding 时，用户会一口气抛出一串"需求"——而且常把**目标、方案、偏好、约束混在同一层**表达出来。核心问题不是"用户懂不懂技术"，而是这几样东西没被分开：

1. 他嘴上说的需求，未必是真目标（可能没认清、或没用语言表达出来）。
2. 他顺手给的"技术方案"**先视为候选手段**——不是不信他，而是先校验角色；但**明确的环境限制、接口契约、以及用户拍板的决定仍须保留**。

所以真正的杠杆在**需求分析**：把混在一起的先归位，往下挖到**朴素诉求**（我到底想少造什么轮子、少干什么重复活、图什么方便、少犯哪种错），可替换的手段留给挖完后的方案设计。核心是**校验角色，不是不信用户**。

用户的三个痛点，一句话各一条：

- 手段冒充目标（"不重复造轮子"被当成跟"省力"平级的需求）。
- 偏好冒充约束（"代码尽量小"没有设备上限却主导架构）。
- 需求越聊越多、无限膨胀。

## 二、这是对 reality-check 的改造，不是新建

- **改造对象**：现有 `skills/reality-check`（v0.3.0，回头用大白话讲"这玩意儿现在能干啥/差啥"）。
- **改造后**：`skills/clarify-needs`。reality-check 目录/定位不再保留。
- **老功能的去留**：功能视角的盘点（"能用的 / 写了没验 / 空壳"）**彻底舍弃**。理由（用户原话）：*解释到底能干啥，终究是技术层面的；根本还是描述实现了用户的哪些需求，这才是大白话有用的。* 所以回头那头不消失，而是**从"按功能盘点"改成"按需求盘点"**。

## 三、骨架：一个 skill，同一根需求脊梁的两头

skill 一进门先分岔——判断用户此刻在哪一头：

```
开口 ──→ 挖真需求(目标缺失才挖) → [归位(5角色) → 分级(4档) → 劝退]仅按需进厚版 → 落一张 NEEDS.md
                                                          │
回头 ──→ 找/重建 NEEDS.md → 逐条对现实 → 大白话讲"哪些做了/哪些没"（默认只在对话说）
```

> **注（§十六 定稿）**：上图方括号里的"归位→分级→劝退"是**厚版**内容，**默认薄核不全走**——只在触发门命中时读 `references/deep-needs-analysis.md`。薄核开口默认只做：目标缺失才挖、轻查偏好/验收、四组大白话落 NEEDS.md。

两头共用**同一张需求清单 `NEEDS.md`**：开口把它挖出来落盘，回头拿它对现实。这是"一个 skill 而不拆两个"的根本理由——拆了就得在两处各写一遍清单契约、还得同步。

### 为什么不拆成两个 skill
- 共用 NEEDS.md 是最硬的粘合点；回头那头离了开头产出的清单没法单独用。
- 前后**是同一个目的（需求真相）落在两个时刻**，不是两个目的，所以不构成"糊"。
- YAGNI：一个文件能讲清就别开两个。真到回头那头长出大量独立逻辑再拆不迟。
- 代价（触发时机相反）由"进门分岔"消化：一进来先分清刚开口还是回头。

## 四、5 角色透镜（归位的骨架）

每条用户原话按角色**归位**——这是**透镜，不是要逐格填满的表**：

| 角色 | 核心问题 | 默认处理 |
|---|---|---|
| 目标 | 用户最终想改变什么？（换掉所有实现方式后它还成立吗） | 保护核心目标 |
| 手段 | 准备用什么办法实现？ | 默认可替换 |
| 验收 | 做成什么样才算能用？（把"美观""稳"翻成可观察标准） | 先定最低及格线 |
| 约束 | 哪些边界不能突破？（有明确来源和违反后果吗） | 区分硬约束 vs 偏好 |
| 交付 | 谁以什么形式拿到？ | 只做首批真实用户要的形态 |

**铁律：按语境归位，不按关键词机械分类。** 同一个词角色可能不同：

- "共享给同事协作"可能是**目标**；"生成分享链接"是**交付**；"部署成网站方便共享"是**手段**。
- "代码体积小"有明确设备上限时是**约束**，没上限只是**质量偏好**。
- "必须用 Python"来自部署环境限制是**约束**，只是习惯则是**偏好/手段**。

### 为什么是"5 角色"而不是"10 话题维度"
挖掘时曾考虑一张 10 维话题表（省力/复用/性能/美观/共享…）。**否决**：那张表自己就混层级——把"复用借力"跟"省力"平级并列，可复用只是省力的一种**手段**。真正治痛点的是**角色**这根轴（目标/手段/约束/验收/交付），不是话题。话题表降级为下面的"防漏清单"。

## 五、分级：4 档（跟角色是两列，别混成一根轴）

| 档 | 含义 |
|---|---|
| 核心 | 删了项目就没存在意义（核心用户/核心问题/核心结果） |
| 底线 | 缺了它，核心目标就无法真实落地（最低验收、硬约束、必要交付） |
| 可换可降 | 有价值，但做法可替换、程度可降（首选手段、体验优化、工程偏好） |
| 当前不做 | 挂不回目标 / 重复 / 无证据 / 成本失衡 / 面向假想的未来场景——**含"延后"和"放弃"两种** |

**"目标不砍"要修正**：不是所有目标都不砍。准确说法——**核心目标不因实现困难被偷偷删除；次要目标、后来冒出的新目标，可以拆分、延后或放弃**。一个项目最好只有一个核心目标；多个互相独立的核心，通常意味着该拆成多个项目/阶段。

## 六、留厚 vs 砍掉（本设计的核心取舍原则）

判据一句话：**能逼出思考的（问题 / 透镜 / 决策）→ 留，且可留得厚；能不动脑填满的（表格 / 模板 / 打分字段）→ 砍。**

危险不是"重"，是**仪式感冒充分析**——AI 把表填完就以为思考完了。（注：reality-check v0.3.0 减重的真实驱动是"重读整个代码库"那份计算开销，需求分析阶段没这开销、便宜；所以这里砍的理由**不是"太慢"**，而是"填格子冒充思考"这一条独立成本。）

**留厚（都是问题/透镜/决策）：**

- **证据判断**：当成一个**问题**问——"这是他真遇到的，还是他猜的？" 不搞 E0–E3 分级打分。（vibe coder 嘴上的需求未必是真需求，这一问直接治"别信嘴上的"。）
- **劝退五问**（**先由 AI 在内部对每条可疑需求逐条判断**；只有答案未知且会改变归位/分级时，才向用户追问，一次只问一个最关键的——见 §十六 与厚版开头）：
  1. 删掉它，核心价值会消失吗？
  2. 换一种实现，用户还满意吗？
  3. "做好"的失败标准是什么？
  4. 这是现实强制，还是个人偏好？
  5. 首个真实用户现在就需要它吗？
- **分级 4 档**（见上）。
- **Appetite 原则**："这问题最多值得花多少成本解决"（不是"估计做完要多久"）。放不下时按固定顺序砍，**绝不偷删核心目标/最低验收**：
  `归入当前不做（含延后）→ 降级可换可降 → 换更便宜的手段 → 缩小交付面 → 质量降到最低验收 → 拆出次要目标`。仍放不下就让用户三选一：加投入 / 缩拆目标 / 暂不做。

**砍掉（填完就冒充分析）：** 8 字段需求卡、11 节输出模板、E0–E3 证据分级、P0/P1/P2/P3/X 五档细打分。内部可以有结构，但不能是"死模板"。

## 七、挖到什么程度算够（开口那头的停手判据）

停在一个**甜区**，同时满足：

1. **剥干净可替换的实现手段**——锚里不含那些**可以换**的方案词（"用 Excel""做个按钮""写爬虫"），只剩"想达成什么 / 想少受什么罪"。**但不可替换的外部协议、运行环境、合规要求（如 Modbus、必须离线、Windows-only）不是手段，归入约束，不许剥掉。**
2. **还没滑到空泛动机**——停在"少造什么轮子 / 省什么力 / 少犯哪种错"这一层；再往下问"为什么想省力"就是空话，砍掉。

例：用户说"给我做个爬虫抓这些网页存 Excel" → 剥方案 → "想把散在几十个网页的数据凑一张表" → 再问一层 → "我每周手动抄这些，烦死了想省这个力"（**停这儿**）。

真需求锚的格式（一句话，**不含可替换的实现手段**；不可替换的协议/环境/合规写进约束）：
> 在【场景】下，【谁】想从【现状】变成【目标状态】，为了【朴素价值】。

## 八、缩放闸（软）

- 需求分析便宜（在对话上推理，不啃代码），所以门槛放低：**小活也顺手锚一句真需求就开干**，不必起全套。
- 只有**需求真的多**、或出现**手段冒充目标 / 偏好冒充约束**这类冲突时，才拉出全套（5 角色归位 + 分级 + 劝退）。
- 反过来：给跑完即弃的微脚本硬套整套归位分级 = 过度工程，禁止。

## 九、产出

- **给用户的出口永远是大白话，一屏封顶**：
  - 我理解你真正要解决的是……
  - 第一版必须做到……
  - 你提到的这些做法可以替换，技术方案留到下一步（brainstorming）比较……
  - 下面这些可以换做法 / 暂时不做……
  - 如果超出投入，我会先从哪里砍……
  - 术语、层级名、架构名一律翻译掉。判据：这段能不能念给不懂代码的人听。
- **落盘 `NEEDS.md`（轻，两头共用）**：真需求锚 + 分级清单，就这些，**不是** 11 节模板。**清单用四组大白话写**（第一版非做不可 / 必须达到的及格线 / 做法可以替换 / 这一版先不做），是内部 4 档（核心/底线/可换可降/当前不做）的大白话映射——**NEEDS.md 里不写内部档位名**（它也是用户可能翻开看的文件）。分两区：
  - **当前需求区**：项目当下有效的需求。用户明确取消/替换需求后，**允许覆盖更新**（否则回头盘点会把废需求当成缺口）。
  - **回看记录（可选）**：如需落盘一次回头结果，按日期追加、不改历史。默认回头结果**只在对话输出，不强制每次追加**。
- **回头找不到 `NEEDS.md` 时**：先从对话、现有文档、用户陈述**重建需求**，交用户确认后再盘点；**不能退回按功能盘点**。
- **回头盘点的诚实边界**：按需求讲每条做到/没做；**没有实际验证依据时（代码在但没跑过），不许说"做好了"，改说"看起来做了，但我没替你实际试过"**。这是**需求状态**，不是恢复"能用/没验/空壳"的功能分档（那套已废）。
- **AI 内部**用 5 角色 / 证据一问 / 分级 / Appetite 归位排级；**用户耳朵里只听大白话**。别让 vibe coder 去学这些术语。

## 十、防漏清单（可选提醒，不参与排级）

主链走完后，AI 可用 **"快、省、用、爽、稳、传、安、控"** 自检有没有漏问某类关注点（离线？以后自己能改？隐私？）。

**铁律：防漏清单只负责提醒 AI 去问，不自动产生需求，更不参与排级。**

## 十一、与邻居划界

| 对象 | 它是什么 | clarify-needs 的不同 |
|---|---|---|
| brainstorming | 在明确的需求上探索方案、比较取舍并获得用户确认 | clarify-needs 是它的**可选前置输入**，不替代方案设计与用户批准 |
| cut-scope | 事后、只读，砍已迭代多轮的**设计** | 开口就介入，挖**需求**并防膨胀（前置的、可落盘的） |
| living-blueprint | 机器读的"现在是什么" | 人读的"你的哪些需求做了/没做" |
| reality-check（旧） | 回头按**功能**盘点能干啥 | 回头按**需求**盘点（功能视角已废） |

**与 brainstorming 的分工（前置且并存，不是替代）：**

- `clarify-needs`：厘清 what / why / 边界 / 优先级。
- `brainstorming`：需求明确后，由 **AI 提出并比较技术/设计方案，用户保留最终确认权**。
- 关系链：`clarify-needs → NEEDS.md → brainstorming → 实现计划`。
- 用户不需要凭空发明技术方案，但**不能被剥夺方案批准权**。
- **触发**（写进 SKILL.md description 的意向）：*Use when a request mixes desired outcomes with proposed solutions, preferences, constraints, or expanding scope; when the user wants to clarify the real requirement; or when returning to compare current reality against `docs/NEEDS.md`.* —— 不因"用户要做东西"就自动触发；需求已清楚的小任务只做一句锚定。

## 十二、反模式

- 在需求还没厘清时就逼用户拍技术方案；或反过来，剥夺用户对方案的批准权。
- 把用户嘴上的需求 / 顺手给的方案当成真需求，照单全收。
- 手段冒充目标、偏好冒充约束没被识别就往下做。
- 用术语/架构名跟用户讲（听不懂 = 白讲）。
- 把 NEEDS.md 堆成 11 节模板 / 填满 8 字段卡就以为分析完了（仪式冒充思考）。
- 给跑完即弃的微脚本硬套整套归位分级（过度工程）。
- 改「回看记录」里的历史条目（那部分只追加）；反过来，需求已被用户取消/替换却不更新「当前需求区」，把废需求当缺口。
- 偷偷删核心目标/最低验收来假装项目做完了。

## 十三、理论来源（只当读物，一个字不进操作指令）

BMM / KAOS（目标 vs 手段）、Impact Mapping（目标→交付因果追溯）、Continuous Discovery Habits（真需求 vs 未验证的猜想）、Shape Up（Appetite 固定投入、范围可变）、Software Requirements / ISO 29148 / ISO 25010（正式底座，不整套搬）。轻量版只借骨架。

1. `skills/reality-check/` → `skills/clarify-needs/`，**两个文件**（见 §十六）：`SKILL.md`（薄核）+ `references/deep-needs-analysis.md`（厚兜底）。
2. 破坏性改动：true-north 版本 0.3.0 → 0.4.0；更新 `.claude-plugin` manifest、marketplace 注册、README 的四件套描述（reality-check → clarify-needs）。
3. 旧的 `docs/REALITY-CHECK.md` 用户日志：属历史，不迁移；clarify-needs 用 `docs/NEEDS.md`，是另一份产物。
4. 发布：推 GitHub + 重部署 user-level（按 true-north 既有发布流程）。true-north 是 Claude Code 插件、**无 vsix**。

## 十五、验收场景（写 SKILL.md 前先做 RED 基线）

按 superpowers TDD：先用这些场景做**无 skill 的 RED 基线**（当前不装 clarify-needs 时它们会失败/表现不佳），再让 SKILL.md 把它们逐条转 GREEN。

1. 用户给出方案（"用爬虫抓下来存 Excel"）时，能否挖出**目标**而不照单全收。
2. 用户给出真实硬约束（"必须离线 / 走 Modbus"）时，会不会被当手段**错误替换**。
3. 小任务（"帮我改一批文件名"）是否**只锚一句真需求、不生成 NEEDS.md 文档**。
4. 回头时是否按**需求**盘点，而非复活功能分档（能用的/空壳）。
5. 回头找不到 NEEDS.md 时，是否**先重建需求并交用户确认**，而不是退回按功能盘点。
6. 与 brainstorming 连用时，是否由 **AI 提方案、用户确认**（clarify-needs 不替用户拍方案）。

## 十六、RED 定稿：薄核 + 厚兜底（渐进披露；覆盖 §四–§十的"操作分层"）

> 依据：`2026-07-15-clarify-needs-red-baseline.md`（19 场景，Claude 子 agent 实测）。**本节的分层结论覆盖前文** ——§四–§十的内容**不变、不删**，但它们从"默认操作步骤"重新定位为"**厚版内部推理工具，按需拉取**"。

### 16.1 为什么分层（RED 事实）

19 个场景里，默认 Claude **真正掉链子的只有 6 个、且轻重悬殊**：强而可靠的只有「挖目标」；「软及格线诚实边界」「偏好盘问」为真；「无 NEEDS 重建确认」「验收翻译」为窄/温和。**专门为逼出"分级/劝退失败"设计的场景 7/12/13，默认全部靠自身推理通过**——5 角色 / 4 档 / 劝退五问 / Appetite **没有一个失败的 RED**。

按 TDD 纪律，无失败 RED 的机制不写成默认必填步骤。但**只在 Claude 上验证过**，弱模型未必自带这些推理——故不删除，收进按需加载的厚版，作**跨模型兼容兜底**。

### 16.2 文件结构

```
skills/clarify-needs/
├── SKILL.md                     # 薄核：默认路径，只放实测有效的
└── references/
    └── deep-needs-analysis.md   # 厚兜底：完整 5角色/证据一问/4档/劝退五问/Appetite+固定缩减顺序/防漏清单
```

### 16.3 SKILL.md 薄核只留（实测有效）

- 进门分岔（开口 / 回头）。
- **开口**：目标未明确时**先挖目标**（唯一厚写的硬步骤，治场景 1）；**轻查偏好**（"这是硬上限还是偏好？来源/后果？"，治场景 8）；**轻查验收**（把"简单/好看/稳"翻成最少几条可观察标准，治场景 10）；能一句话锚出真需求就锚（不含可替换手段；协议/环境/合规归约束不剥）。
- **回头**（薄）：有 NEEDS 直接按它逐条盘 → **诚实边界**：没运行证据不说"达标"，只讲需求不掺代码质量挑刺（治场景 4′）；无 NEEDS 先**重建 + 显式摆出来交用户确认**再盘（治场景 5）。
- **缩放闸**：小活/微脚本只锚一句就开干，**永不进厚版**。
- **大白话铁律** + NEEDS.md 两区写法。

### 16.4 何时读厚版（触发门，**与缩放闸 AND**）

先过缩放闸——**跑完即弃的微任务一律不进厚版**。在此前提下，出现任一即读 `references/deep-needs-analysis.md`：

- 用户明确说"深挖 / 严格分析 / 完整归位"。
- 写不出一句不含可替换手段的真需求锚。
- 出现 **两个以上**独立用户或独立目标。
- 需求明显**装不进**用户投入（时间/精力上限）。
- 分不清某条是**手段 / 偏好 / 硬约束**。
- AI 对**怎么分级**没把握。
