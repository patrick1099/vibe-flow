# 认知四象限（Fable Field Guide）借鉴决策

> 日期：2026-07-30（源头讨论 2026-07-17，当时停在岔路上未落地）
> 来源：Anthropic《A Field Guide to Claude Fable: Finding Your Unknowns》，Thariq Shihipar，2026-07-06
> <https://claude.com/blog/a-field-guide-to-claude-fable-finding-your-unknowns>
> 一句话：**吸收一条框架（手段太死/目标太空）+ 一招（原型与参照物），刻意不收盲区扫描。**

## 1. 原文骨架

四象限（"你意识到 / 没意识到" × "你知道 / 不知道"）：

| | 意识到 | 没意识到 |
|---|---|---|
| 知道 | **已知已知**：写进 prompt 的 | **未知已知**：看到才知道自己要什么（审美、品味） |
| 不知道 | **已知未知**：知道该问什么 | **未知未知**：连问题都提不出的盲区 |

配"**地图 vs 领土**"：地图＝你的 prompt / skill / 上下文，领土＝真实代码库与现实，**两者落差就是你的 unknowns**。核心断言：模型强到一定程度后，**质量瓶颈从模型能力转移到人澄清 unknowns 的能力**。

招法：盲区扫描（未知未知）、原型与参照物（未知已知）、访谈式提问（已知未知）、计划评审、实现笔记、Pitch、Quizzes。

## 2. 对照结论：≈80% 是背书，不是缺口

拿四象限逐格对 clarify-needs v0.4.0：

| 象限 | 原文的招 | 本插件已有 | 判定 |
|---|---|---|---|
| 已知已知 | — | clarify-needs 总纲：请求把目标/方案/偏好/约束混一层，拆它就是入口 | 就是原料 |
| **已知未知** | 访谈式提问，优先问会改架构的 | §1 挖目标回问 why；厚版 §四"只问会改变归位分级的、**一次一个**" | ✅ 连"优先问改架构的"都已有 |
| **未知已知** | 原型试选 + 参照物 | 原先明确甩给 brainstorming | ⚠️ 见 §3 |
| **未知未知** | **盲区扫描** | 只有厚版 §七防漏清单，且是**被动**清单 | ⚠️ 真空格，见 §4 |

另外两处独立背书（不改任何东西，但值得记）：

- **原文给每一招都配了 "when NOT to use"**（brainstorm 不用于已锁死的清晰问题；references 不用于你能说清时；notes 对 trivial 任务是过度）——这正是本插件的**档位 + 各 skill 缩放闸**哲学，被官方独立收敛验证。
- **Quizzes / Pitches 打的是"事后的理解校验"**，不是需求回顾——不属于 clarify-needs 回头那头，另一路，不收。

## 3. 采纳的两项

**① spec 平衡轴 → `clarify-needs` 总纲（v0.5.0）。** 原文点了一条更锋利的表述：

> 太具体 → Claude 会照你说的做，**即使该 pivot 也不 pivot**；太模糊 → Claude 按行业最佳实践**瞎猜**，未必合你。

这是 clarify-needs 存在理由的升级版：旧总纲只说"混在一层"，是个**对称**说法；真实的病是**有方向的失衡——手段说太死、目标说太空**。落地成一张两列表（说太死 → 松开：确认是真约束还是可替换手段；说太空 → 钉实：翻成看得见的标准），并点明薄核三步各治哪一头。**纯换框架，零新机制，不加流程步骤。**

**② 原型与参照物 → `vibe-flow` §4 探方案（不进 clarify-needs）。** 未知已知那格原判"已划界甩给 brainstorming"，但 2026-07-30 合并后 brainstorming 已在插件之外，探方案被 §4 自己接了；而"看到才知道自己要什么"（界面 / 观感 / 交互）正是 vibe-apps 分支最常见的场景。补的规则：**别追问"你想要什么风格"（用户答不出）**，改成给 2–3 个小原型让他挑；说不清就请他扔参照物（截图 / 链接 / 现成产品），**用示例替代提问**——比问更省，符合"小事要省"。

放 §4 而不放 clarify-needs 的理由：这是**探方案**动作，不是澄清需求；塞进 clarify-needs 会破坏它 stack-independent、不产原型的边界。

## 4. 刻意不收：盲区扫描（未知未知）

原文要求盲区扫描喂**"你是谁、你懂什么"的知识画像 + 让 Claude 读代码库（territory）**。这两样输入 clarify-needs **故意都不碰**（stack-independent、不读代码库），硬塞会破边界。所以它不是 clarify-needs 的公民。

宿主候选的演变：

- 2026-07-17 曾倾向 brainstorming 或 scan-field。
- 2026-07-30 复核：**scan-field 也不是它** —— scan-field 开口那头读的是**市面**（外部同款），不是本项目 territory。两者搜索对象根本不同。
- **当前最强候选：`cut-scope` 的镜像。** cut-scope 已经在读 BLUEPRINT + 代码 + transcript，已经有"fresh subagent 冷眼"这套机制。盲区扫描与它是**同输入、反方向**的一对：cut-scope 找「多做了什么」，盲区扫描找「没想到什么」。

**待验，不焊。** 动它之前必须先过 RED：**证明默认 Claude 被要求"扫一下这块的盲区"时会失败**。若默认就扫得不错，它不该进任何薄核（这是 clarify-needs 整套 19 场景实测立下的规矩，也是 reality-check v0.2.1 翻车的教训——别把"我认为重要的风险"当用户价值往里堆）。

## 5. 也不收：during（实现中）那个洞

原文案例里未知未知是**逐阶段反应式**冒出来的，implementation-notes 就是"实现中撞到的未知未知"。这暴露一个结构事实：clarify-needs 只有**开口 + 回头**，中间的 during 是空的。

**不补。** 那本就是 `superpowers-manual` 的 `executing-plans` 的地盘；vibe-flow §8 已经要求"遇到会改变行为的冲突时指出并等用户决定"，够了。一句划界即可，不为对称性造第三头（参见同日 scan-field 的教训：对称好看，价值不一定对称）。
