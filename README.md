# vibe-flow

一套完整但不重的个人 vibe-coding 工作流。承重的只有一个显式档位：**小事要省，大事要好。**

省的是流程，不是质量；好的是该厚的地方厚，不是每次走满。重流程框架的病不在「太严谨」，
在于只有一档，所有事一律走满。

## 项目架构讨论与 Clean MVVM

0.24.0 将新项目的架构讨论纳入开工流程，并提供可选的 Clean Architecture + MVVM 契约。
现有应用不会因此自动迁移。

每次开始新项目，AI 先根据业务、交互状态、设备与后台任务、维护成本推荐结构，说明职责和状态归属、
取舍与验证方式，方向谈定后再实现；你已明确方向或授权 AI 决定，就直接推进。简单脚本一两句话即可，
小界面可以只分开界面与纯逻辑，复杂应用重点考虑 Clean MVVM；不为架构名字造空层。
已有项目的普通修改沿用已定方向，需要迁移时再明确范围。

选定 Clean MVVM 后，业务、用例与资源生命周期、展示状态、界面、外部 IO 分工明确，源码依赖向内。
原生应用默认由 UI 线程持有可变 ViewModel，后台传回普通结果；真正退出走同一个幂等清理流程。
小应用可以少量文件承载这些职责，原生与 Web 技术路线保持不变。

验证随本次规模安排：小改复用已有检查，新项目或明确迁移落实讨论中约定的检查；自动覆盖与人工核对
分别说明。依赖、无窗口行为测试不替代实际界面和设备验证，也不表示已为所有应用安装架构检查。

完整入口见 [新项目架构讨论](skills/vibe-flow/SKILL.md)，
可选契约见 [Clean Architecture + MVVM](skills/vibe-apps/references/clean-mvvm.md)。

## 装

```
/plugin marketplace add patrick1099/vibe-flow

```

入口是 `vibe-flow`。它判一次档，澄清厚度、探不探方案、叫不叫另一个 AI 审、验证强度、收工后要不要
回头，全是这一次判定的下游。要不要留文档不归档位管，看工具寿命（见下「两条不分档的底线」）。

## 判档判的是什么

```
「帮我写个脚本把串口日志转成 csv」
  → 省档。不额外澄清需求；新项目用一句话谈定结构，已授权 AI 决定就直接做；
    最小可用，写完拿代表性输入跑一遍；不到 100 行的微脚本只写头部说明，不另建文档

「我要做个抓包分析工具,做完发给同事用」
  → 好档。命中「范围大」→ 先挖需求分清偏好与约束、讨论架构方向，有实质技术取舍时请另一个 AI 审、
    落 NEEDS.md;因为要给别人,还要打包后实际用一遍再交

「这个抓包工具导出时列名改一下」(工具已经用了半年)
  → 省档。明确的小改,直接改、跑一遍、把 CHANGELOG 记上
```

判档只看**这次改动**，命中任一即好档：

- 范围或影响面大：新加一整块功能、要新建的工具本身就复杂；或改动虽小但一错就影响全部数据（单位换算、统计口径）。
  「新建」本身不算——需求清楚的小脚本，新写也是省档
- 出错后果重 / 不可逆：删除 / 覆盖 / 迁移数据、联网上传、发出去收不回
- 关键未知：有会实质改变行为、数据或方案的未知
- 多目标纠缠：两个以上独立目标或用户

工具要用多久、给不给别人，**不影响这次走多厚**，只影响要不要留文档、要不要按交付形态验证。
一个长期工具上的明确小改就是小事。

默认省档，升到好档必须说得出理由。但省档只给一眼看得出的明确小改，**拿不准命没命中，按好档走**，
并在回复里说一句。你一句话可以直接定档，优先于以上判据：「这个随便做一下」→ 省档；「这个要做好」→ 好档。

## 九个 skill

| skill | 环节 | 触发 | 是否改文件 |
|---|---|---|---|
| `vibe-flow` | 总入口：判意图 → 判档 → 路由 → 决策边界 → 验证收尾 | 建/改/扩一个脚本、工具、应用、功能 | 只改你要它改的 |
| `clarify-needs` | 明确需求：把目标 / 方案 / 偏好 / 约束分开 | 手动，或需求不清的大活（新项目、新一整块功能）动手前自触发 | 写 `docs/NEEDS.md` |
| `living-blueprint` | 留意图与交接：当前全貌 ＋ 为什么变更 ＋ 交接入口 ＋ 进度快照 | 微脚本以外的脚本 / 应用必带；一批改动收工时由派出的 fork 加载，干活的主 agent 不加载（只往 HANDOFF「已谈定」区记谈定的事） | 写 `BLUEPRINT.md` ＋ `CHANGELOG.md`（＋`AGENTS.md`、按需 `HANDOFF.md`） |
| `vibe-scripts` | 实现：独立 Python 脚本的四层五区 + 分级 | 写/改独立脚本前 | 写脚本 |
| `vibe-apps` | 应用入口：原生桌面 / Web 界面路由、共用边界、界面效果图先行（DESIGN.md + HTML 效果图 + 截图对照） | 搭 GUI 应用脚手架前；新应用 / 新页面 / 布局大改写界面前 | 写应用、`DESIGN.md`、效果图 |
| `vibe-apps-native` | 原生桌面：默认 Python + ttkbootstrap，明确选择纯 Rust 时固定用 Slint | 已选原生路线后 | 写应用 |
| `vibe-apps-web` | Web 界面：默认 Python + FastAPI；桌面 Web 壳加 pywebview，网站用浏览器 | 已选 Web 路线后 | 写应用 |
| `cut-scope` | 回头剪枝：冷眼核对真实需求 vs 已膨胀的设计 | 手动，迭代多轮后 | 只读，只给方向 |
| `scan-field` | 对外扫同款两头：开工前查市面有没有 / 完工后产原创度对比 | 手动，或由 vibe-flow 路由 | 只产结论 |

应用先由 `vibe-apps` 选路线，再只加载选中的那个分支。新建本地工具、上位机默认原生 Python + ttkbootstrap；
要浏览器访问或网站交付才走 Web（FastAPI，桌面壳再加 pywebview）。明确选纯 Rust 时走原生 Rust，界面固定用 Slint。
用户已指定的技术和已有项目的现有实现优先，普通修改不触发迁移。

新应用、新页面、布局大改，写界面前先出效果图：项目根 `DESIGN.md` 定颜色、字体、间距，AI 按所选框架的能力
画一个可切换状态的 HTML 效果图，你在浏览器里改到满意；再照图实现，第一版布局出来 AI 就截应用窗口和效果图
并排对照、修完差异再给你看。小改沿用已有设计，不重画。原生应用（ttk / Slint）的主题不手抄：
`vibe-apps/scripts/design_theme.py` 从 DESIGN.md 生成主题文件，同时把同一批值写进效果图，两边出自一处；
DESIGN.md 里有框架还原不了的写法，它直接报错指出哪一行，不悄悄丢掉。

`clarify-needs` 会自触发但带闸，只在这次要做的事够大、需求本身又不清时起（开新项目 / 新工具、
新加一整块功能、多目标纠缠、需求越聊越多），明确的小改 / 改 bug / 纯问答不起。闸写在 description 里，是软约束；
误伤了说一句「这个随便做一下」就跳过。`cut-scope` / `scan-field` 两个回头类 skill 是约定式手动。

要做的东西有流程时，`clarify-needs` 会把「它跑起来是什么样」画成图：用 [D2](https://d2lang.com)
写，`skills/clarify-needs/scripts/model_page.py` 渲染成本地网页自动打开，猜的地方标黄色虚线
框，页面底下列出要你拍板的问题。大活涉及多个模块时，开工前还会画一张「我打算怎么搭」图（模块怎么分、
数据怎么流）。新项目首次架构图用于讨论方向；方向谈定后的细化图让你看，不重复审批。分层架构那种靠格子对
齐的图（APP / Driver / HAL / BSP）D2 摆不出来，改写 HTML 片段交给同一个脚本出页面。本机没装
`d2` 时流程图退回对话里的 ASCII 图。

## 两条不分档的底线

**低耦合，变化轴可插拔。** 逻辑和 IO / 界面分开，微脚本也一样。以后会增、删、换的那类东西
（平台、格式、厂商、数据源）叫变化轴：一个成员时代码聚在一处，第二个出现时收成一张注册表，
加或去掉一个成员只动它自己和注册表。成员各自依赖外部东西（第三方库、设备、网络）时，再做到
一个坏了不拖垮其他。细则以入口 `vibe-flow` §5 和 `skills/vibe-flow/references/low-coupling.md` 为准。

AI 平台（Claude Code、Codex……）是一条特殊的轴：用到 hooks、插件清单这类平台能力的项目，先只做正在用的
平台，不一口气做全；没有统一选择平台的调用方时，各平台自己的清单就是入口登记，不另造注册表（有这样的调用方，
照一般变化轴收口）。出生时把路留好（判定逻辑放在跟平台无关的
一处，蓝图第 6 节写清要在什么时机做什么、平台缺这能力时怎么降级），以后换到哪个平台要用，由那个平台的 AI
自己适配；它发现这次要用的功能在本平台还没适配时，会先问你一句要不要现在做。细则在
`skills/vibe-flow/references/platform-porting.md`。

**两份文档。** 微脚本以外的脚本和应用都带 `BLUEPRINT.md`（现在是什么）和 `CHANGELOG.md`
（为什么变成这样：起因引用户原话、根因、改成什么、没选的路）。按目录归属放：独占一个目录的放
`docs/` 并带 `AGENTS.md`，和别的脚本共处的用同名旁挂文件。什么时候改哪份见 `living-blueprint`，
哪些项目要哪些文件以入口 `vibe-flow` §6 为准。代码改了哪几行交给 git。

**文档交给收工 fork。** 维护这几份文档要读规则、读文档、改文档，全压在负责实施的 AI 的上下文里，
正事就做得慢、做得笨。所以一批改动做完、交付之前，由执行负责人派一个继承其执行上下文的 fork 去维护，
等它完成、核对没碰代码再汇报。直接实施时由主 AI 派；采用下文的批次监工模式时由监工派，复核和文档收尾
都在监工层完成，不让主会话读回执行细节。监工在执行期间只持续保存 HANDOFF 的批次状态区；谈定约定仍由主会话记录。
没有这种子 agent 可用时，由执行负责人按 `living-blueprint` 自己整理。

**谈定就记，动手前读回。** 上面那条只管收工；从谈定到收工这段时间，结论只活在对话里：对话一压缩就丢细节，
丢的常常是最早、最根本的那句，来回纠正时又容易只盯最新一句。所以讨论中每谈定一件事（你第一次说出的核心目标和
硬约束、你点头的做法、你纠正过的理解、codex 审完 AI 采纳或否掉的结论），干活的 AI 当场往 `HANDOFF.md` 的
「已谈定」区记一条，一两行，不加载别的规则；接手、恢复或压缩之后，动手前先把这一区和 `NEEDS.md` 读回来对照。
你指出"我说过的被漏了"时，它按全部有效约定整体修正，不只改最新一句，也不让你把说清的再点一遍头。
收工时 fork 把这一区分流进 NEEDS / BLUEPRINT / CHANGELOG。细则见入口 `vibe-flow` §4。

Claude Code 上有个兜底：对话压缩后（手动、自动都算），`hooks/compact_anchor.py` 从当前目录往上找带「已谈定」区的
HANDOFF，把原文注入给 AI，并提示去读 NEEDS.md 的当前需求区（只有 NEEDS 的项目也提醒）；同一目录几个脚本各有
HANDOFF 时标明每份管哪个脚本；太长就只列路径、要求读完，不截断。它不拦压缩：
HANDOFF 有没有改过判断不了该记的有没有漏记，拦了反而要你来提醒 AI。Codex 侧这一版没接。

这一条有闸，Claude Code 和 Codex 都能用。Claude Code 的 Stop hook（`hooks/doc_gate.py`）从
本轮记录里找成功的 Write / Edit；Codex 入口（`hooks/doc_gate_codex.py`）在每轮开始时记下时刻，用
PostToolUse 收集本轮成功的 `apply_patch` 文件，在 Stop 时检查。两边还会扫一遍当前 git 仓库里本轮开始后
改过的文件，所以经 shell / Python 落盘的改动也算。两边共用 `doc_gate.py` 的项目识别、文档位置判定和提醒：
缺文档、或两份文档都早于这批代码的最后一次修改时只拦一次，提示去派 fork；AI 判断这批不用记时，跑提示里
给出的回执命令（`doc_gate.py receipt --blueprint <路径> --reason "<一句话>"`）写一条回执，之后同一状态不再提醒——
后台任务完成把 AI 唤醒、本轮再结束一次，也不会把同一批改动重拦一遍。
文档跟没跟上只看磁盘修改时间，fork 写的也认；Claude Code 上 fork 还在跑时先不拦，它完成后再判。
判断仍归 AI，免得为过闸写假条目。

回执一条管一对文档（BLUEPRINT + CHANGELOG），不是一个目录：同目录几个旁挂脚本各管各的。指纹按这对文档管的
整份代码快照（项目根下 git 跟踪的非文档文件加未跟踪的代码文件，旁挂的就是那个同名脚本）再加这两份文档的内容算，
所以它确认的是"当前全部代码都不用更新这对文档"，不只是本轮那几个文件；之后代码增删改、或文档内容变了，回执
自动失效。缺文档不能用回执；待判定的代码不在快照里（被 gitignore 的）、项目超过 3000 个文件、读不了或 git 超时，
回执都验证不了，照常提醒。回执存在 `~/.vibe-flow/doc-receipts/`（每对文档一个文件，原子替换），两个闸和
session-sweep 的文档探测都经同一个判定函数读它，session-sweep 不用改代码。

认不认得出是 vibe 项目靠三种标记：`docs/BLUEPRINT.md`、脚本头部 `结构: vibe-scripts/standard`
或 `toolkit`、AGENTS.md（或旧项目的 CLAUDE.md）里的「架构约束（vibe-apps）」段；没有标记的仓库
（比如公司代码）一律不管。文档该放哪先看已有布局（旁挂文件、`docs/`、`AGENTS.md`），看不出来就
把两个位置都列出来，不猜。

Codex 的配置随插件分发：`.codex-plugin/plugin.json` 指向 `hooks/codex.json`，不用改用户的全局
`config.toml`。新装或钩子定义变化后，须先在 Codex 中审阅并信任钩子（CLI 用 `/hooks`）；未信任、
hooks 功能被关闭或管理员禁用插件钩子时不会执行。当前在桌面引擎 `0.155.0-alpha.16.3` 实测真实
`apply_patch` 回执。Windows 在 workspace-write + elevated 配置下，插件钩子以宿主用户运行，
`py -3` 可正常启动；工具沙箱里找不到用户 Python 的限制不影响此入口。
机制和分发规则见 [Codex Hooks](https://learn.chatgpt.com/docs/hooks) 与
[插件钩子文档](https://developers.openai.com/plugins/build/plugins#bundled-mcp-servers-and-lifecycle-hooks)。

Codex 只在插件数据目录暂存本轮开始时刻和文件路径，按会话、回合和工具调用隔离，Stop 或 Interrupt 后
清理本轮记录；不读取会话日志。用户原有的 git 改动不算成本轮修改：git 扫描只收修改时间晚于本轮开始的
文件，未跟踪的新文件只收代码类后缀，跑工具产生的数据、日志不算。边界：别的 git 仓库里经 shell / Python
落盘的改动看不到；Codex 也不收集其他 MCP 写文件工具；钩子装上之前就已开始的那一轮没有开始时刻，
不做 git 扫描。删掉的文件按所在目录的修改时间算，所以本轮之前删掉、还没提交的文件，若本轮同一目录
又有文件增删，会被多算一次（多拦一次，不会漏拦）；要根治得在每条消息提交时跑 git 记基线，每条消息都
变慢，没做。本闸只在主会话 Stop 检查。闸内部出错时提示错误并放行。

fork 回来后怎么确认它没碰代码：`skills/vibe-flow/scripts/code_state.py` 打印一个只随非 `.md` 文件内容
变化的哈希（已跟踪改动、暂存、删除、未跟踪文件的名字和内容），派发前后各跑一次比对。

回归测试：`py -3 -m unittest discover -s tests -v`。
[真实回执及采集记录](tests/fixtures/)来自隔离环境中的原生补丁工具，包含 `Exit code / Wall time / Output`
前缀；解析器在整段输出中定位成功行，并排除非零退出码。

## 已确定计划的批次监工

多任务计划已经谈定、并选用监工模式时，把一个可独立验收的批次整体交给监工。主会话负责计划、必要的用户决策、
接收短简报和启动下一任监工；监工负责派工、日常排错与重试、集成、产出复核、验证和文档收尾；执行者只处理具体任务。
普通失败在监工层解决，深入排错另派短任务。小改仍直接做，不强行分成三层。

同一时间一个监工，默认一个在途执行者。替换只在无在途任务的批次边界进行：先停止新派工，完成或确认终止全部
执行、验证和文档任务，保存交接，再由主会话核对宿主实际运行状态及记录。新监工不继承完整聊天，按计划、有效约定、
HANDOFF 和实际工作区恢复。主会话只收最多八行的状态、成果、必要决策和证据路径，不逐项接回日志、代码与复核。

批次状态复用 HANDOFF 的机器区，用 [batch_state.py](skills/vibe-flow/scripts/batch_state.py) 的 `save` 保存、
`status` 读取短摘要、`check --ready` 检查交接记录。保存会检查内容版本并原子替换，保留区外文字；损坏记录、项目不符或重复标识
会以非零退出拒绝，切换批次须先检查旧批已可交接。记录中仍有运行任务时，交接检查不会通过。实现完成与验证通过分别记录；
证据文件存在只满足机械条件，正确性仍须实际验收。
这个区是当前批进度的唯一出处，HANDOFF 其他文字只留恢复入口，不另造一份进度台账。

## 交接

新开会话接着做、换别的 AI 接手，光有蓝图不够：蓝图只讲「是什么」，不讲「怎么在这干活」和
「做到哪了」，而且新会话只自动加载 AGENTS.md，不会自己去找蓝图。所以再加两份：

- `AGENTS.md`（有自己目录的项目，放根目录）：交接入口。第一段写阅读顺序（HANDOFF → 要动哪块读
  BLUEPRINT 那块 → 再搜 CHANGELOG 里那块的「没选的路」），然后是跑 / 测 / 打包命令、项目特有的坑、
  几行搜不出来的约定。不写完整代码地图：文件在哪 AI 现查就行，写下来只会过时。项目级只建它，两个平台读同一份。
- `docs/HANDOFF.md`：进度快照，只在有没做完的活时存在，覆盖式、一屏以内——已谈定的约定、在做什么、
  做了一半的卡在哪、下一步、等你拍板的、别碰的。「已谈定」区由干活的 AI 在讨论中当场记，其余在活没做完
  就结束会话时由 fork 建立或更新；整件事做完，fork 把「已谈定」迁走再删掉它。

四份各管一件：AGENTS 管怎么干活，HANDOFF 管做到哪，BLUEPRINT 管是什么，CHANGELOG 管为什么。

**同一件事的进度只记一处。** 进度和交接只写 HANDOFF；采用监工模式时，具体任务状态只在其中的机器批次区保存。不写进 pstate 条目，也不写进平台原生记忆或 hub 金库——记忆只存
长期结论和教训。pstate（project-state 插件）管另外两件：会话互斥（几个会话同时干同一个个人项目时，撞上同一个文件由钩子
拦下、问你等还是接手）和待办条目（还没开始的事，一行一条，指向 HANDOFF）。公司仓不建 vibe 文档，也不加锁、不新建条目。
session-sweep 只是发现入口：从它那里捡起一件事，进度落回 HANDOFF，不在它那里维护。

Claude Code 默认只读 CLAUDE.md。想让它读项目的 AGENTS.md，要么启用内置的 agents-md 并把
`instructionFiles` 设成 `claude-md-and-agents-md`，要么在项目里放一个只有一行 `@AGENTS.md` 的
CLAUDE.md。Codex 原生读 AGENTS.md。

## 环节与档位对照

| 环节 | 省档（默认） | 好档 |
|---|---|---|
| 开工前 | 查自己有没有现成的 | ＋查市面有没有（`scan-field` 开口那头） |
| 明确需求 | 不澄清，或只问一个问题 | 挖目标 / 分清偏好与约束 / 翻译验收；有流程的画「它跑起来是什么样」图 |
| 架构讨论（新项目） | 一两句说明适合的结构，谈定后开始；已授权 AI 决定则直接推进 | 讨论职责、状态、IO/任务边界和取舍，谈定后开始 |
| 探方案 | 已定方向内直接做 | 已定方向内的技术取舍由 AI 决定，有实质取舍时请另一个 AI 审；影响你使用的翻译成后果再问；界面类出原型，多模块画图；定稿后三行白话告知就开工 |
| 实现 | 最小可用；守低耦合底线，不预建插口 | 按分支的完整纪律；三点设计里列变化轴 |
| 留文档 | 按工具寿命不按档：微脚本头部契约行；其余 `BLUEPRINT.md` ＋ `CHANGELOG.md`；有目录的＋`AGENTS.md`；有没做完的活＋`HANDOFF.md` | 同左；需求仍演化时＋`NEEDS.md` |
| 验证 | 代表性输入跑通 ＋ 拔插自查；给别人的按交付形态跑 | 按交付形态实际使用 ＋ 针对性测试 ＋ 结构测试 |
| 收工后 | 无 | 膨胀了剪枝 / 完工了扫同款 |

分工：需求我们一起定；新项目开始前也讨论架构，AI 给推荐与理由，你参与决定方向，也可以委托 AI 决定。
方向谈定后的库、文件名、内部 API 和测试工具由 AI 处理；还有会实质影响架构或维护成本的技术取舍时，
交另一个 AI 挑毛病。涉及此前没确认过的体验、数据或范围选择，先说明后果再请你决定。
模块、接口、注册表、分层这类架构词直接用，第一次带一句解释，不把代码细节抛给你。
方案定稿后三行白话告知，多模块的附图，然后直接开工；已确认过的方向不会再让你点一次头。

不命中的环节完全不提。这是路由图，不是阶段清单：把它当必经阶段依次跑，就退回了它要取代的
那种流程。

缺一不可）全部带行号一次列出。输出目标是一条变化轴，两个成员 ttk / slint 收进一张 `TARGETS` 注册表，各自声明校验与渲染。

含义对不上）；效果图 CSS 不单列成目标，绑在原生目标上、出自同一次校验；未知字段报错；Slint 查重名时 `_` 与 `-` 等价；
摘要只取 front matter 且换行归一，改正文不算设计变了。实测后改了两处设计：本机 Esafenet 会加密 python 写出的 `.css`，
浏览器读到密文、效果图丢光样式，而 `.html` 不受影响，所以 token 写进效果图 HTML，不另建 theme.css；Esafenet 不让把
别的扩展名改名成受加密的扩展名（`os.replace` 报 WinError 17），临时文件改为保留目标扩展名。Slint 1.18.1 的 `slint!`
宏能 `import` 外部 `ui/theme.slint`（路径相对 crate 根，改了自动重编），所以写在宏里的项目也能用。验收用同一份
DESIGN.md、同尺寸同数据，HTML 效果图、ttk、Slint 三方截图并排：五处取色三方全等，字号一致（125% 缩放机器上 Tk
负数字号仍是 12px）。验收中查出并写进语言参考：Slint software 渲染器不合成粗体，700 字重要注册 `msyhbd.ttc`；
系统缩放不是 100% 时 Slint 截图先设 `SLINT_SCALE_FACTOR=1`；ttkbootstrap 按钮默认内边距在 26px 高里切字，要在
Style 里收紧。剩下的差异在控件层（ttk Treeview 边框色、选中行内缩），与生成器无关。生成器只出一套颜色，要深浅色
切换的项目（如 serial-split 的 `dark: bool`）照旧手写 Theme。新增 35 项测试，全量 185 项通过。没选的路：无单位
spacing 当像素（codex 建议；规范把无单位数定义为列数或比例，v1 直接报错）；PyYAML 放 venv（codex 建议；插件脚本
约定只用 stdlib，分发出去的插件里 venv 也无处安置）；node 脚本调 designmd 的解析器；ttk 产物用 JSON（打包要多收一个文件）；
单独的 theme.css（本机浏览器读不了）。

（codex 否决：公司仓没有 HANDOFF，跨 worktree 交接仍要它；它零使用的真正原因是"AI 主动记录"这条触发没落实，加上没有
任务时完全静默，不是没用）；把进度统一并进 HANDOFF（公司仓不建 vibe 文档）。

0.20.2（2026-10-09）推翻 0.20.1 里"pstate 管没有 HANDOFF 的仓库（公司仓等）"那半句，只改规矩不改代码；同日 project-state
0.2.0 跟着改。起因是用户整理文件职能时指出："HANDOFF是要接受正在干但没干完。PSTATE是干我同时要做的几件事"，"我当初涉及
pstate就不是为了公司项目吧，我当时说过，公司东西我记得住，不需要。 pstate是为了达到一个类似互斥锁的功能吧"。0.20.1 是按
仓库类型分工（个人仓写 HANDOFF、公司仓写 pstate），两处记的其实是同一种东西；而"公司的我记得住"是用户前一天在 session-sweep
里说的，没被连起来。改成按概念分：进度和交接只写 HANDOFF；pstate 只管会话互斥（撞上同一个文件由钩子拦下、问用户等还是接手）
和待办条目，只用于个人项目，公司仓不加锁、不新建条目。没选的路：保留 0.20.1 的按仓库分工（同一件事两种记法，用户分不清职能）；
把待办也并进 HANDOFF（HANDOFF 做完就删，装不下"还没开始的事"，也表达不了几个会话谁在干什么）。
