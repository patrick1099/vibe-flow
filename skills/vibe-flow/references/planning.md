# 架构讨论与好档方案细化

只在新项目架构讨论、已定架构需要改变，或好档探方案时读相应部分；明确的小改不读。本文件是这些阶段步骤的唯一出处。授权与谈定记录以 [../SKILL.md](../SKILL.md) §4 为准，外援按 [collaboration.md](collaboration.md)。父入口只路由，不预读应用分支。

### 新项目先讨论架构（不分档，按规模缩放）

每次开始新项目，在搭脚手架、写实现前，像讨论方案一样先讨论架构。**先看项目实际情况，再决定采用什么结构**；Clean 分层是有业务、交互状态或设备生命周期的应用的重要候选，不是所有项目的统一答案；展示层另按 `vibe-apps` 的展示状态规则选，不默认 MVVM。

- **AI 先给推荐与理由**：说清项目需要分开哪些职责、状态由谁管理、IO/后台任务放哪、怎样验证，以及这套结构会增加多少维护成本。有实质取舍才给另一个候选，不为凑选项比较框架大全。
- **按规模缩放**：小脚本一句“纯函数处理数据，入口负责文件读写”也可以；小界面可以先用界面与逻辑分离；复杂设备应用再讨论用例、展示状态归属、ports 和生命周期。只弹一次文件选择框的脚本不因此升级为完整 GUI 应用。不要为了架构名字建立空层。
- **讨论到方向谈定再开始实现**：把推荐和取舍说清，让用户能参与选择；用户已明确架构，或已授权“你定 / 直接做”，就按该授权推进，不重复索要点头。内部文件名、具体 API 和测试工具仍由 AI 决定。
- **现有项目普通修改沿用已定架构**：不是每次会话、每次修 bug 都重新讨论；只有新目标让原结构明显不适用、用户要求迁移或需要改变已定边界时，才针对那一部分重新讨论。局部迁移先明确范围，不默认全仓重构。
- **谈定后留下实际结论**：职责与状态归属、采用/不采用的边界及理由、验证方式和适用范围，记入项目已有的架构约束；讨论中先按 [../SKILL.md](../SKILL.md) §4 写 HANDOFF「已谈定」。微脚本仍只用头部契约，不额外造文档。

应用的候选与落地入口见 [vibe-apps](../../vibe-apps/SKILL.md)。此处讨论的是项目架构方向；方向定了以后，下面的方案细化不再重复审批。

### 探方案（只在好档）

- **只有一条明显路**：新项目的架构方向谈定后，不再比方案，直接做（满足下面画图条件时照画）。
- **涉及数据模型、持久化、主要 UI 流程、模块边界或分发方式**：三点短设计“怎么做 / 为什么 / v1 明确不做什么”，**再加一行“变化轴”**：以后会增、删、换的是哪几类东西，各自现在有几个成员（[../SKILL.md](../SKILL.md) §5）。没有写“无”，不许省掉这一行。
- **「我打算怎么搭」图**：好档，且**本次动到**至少两个职责模块、或数据要跨好几个处理 / 存储环节时默认画（按本次实际动到的算，与有没有多条路无关）。画模块怎么分、各管什么、数据怎么流、存在哪，配一两句为什么，随三行白话一起给用户——他懂架构层、不懂代码，藏起来他就没法及时插话。**方向已谈定后的细化图是告知，不重复审批**；新项目首次架构图用来参与上面的架构讨论，不能用“图已发出”代替方向谈定。已定方向内的实现疑点 AI 自己处理（[collaboration.md](collaboration.md)）；新项目尚未谈定的架构方向，以及此前没确认过、会改变使用体验或数据的点，才标 `guess` 并问。用户看图后开口：要改的照改，提问的先解释为什么这么搭，给建议的先判断采不采纳并说理由，别把一句“为什么不这样”当成改动命令。画法见 [run-model.md](../../clarify-needs/references/run-model.md)（`--layer build`，画之前读）。
- **确实有 2–3 条各有取舍的路**：先问一句——**选 A 和选 B，用户用起来会不会不一样？**
  - **不会**（已定架构内的库、代码细分、内部数据结构）：AI 自己定，不问用户；新项目的整体架构方向按本文件的架构讨论处理；好档按 [collaboration.md](collaboration.md) 交决策者审，审完自己拍板。
  - **会**（快慢、能不能离线、会不会删改用户数据、多花多少时间、以后能不能加同类的东西）：把每条路**翻译成用户能感知的后果**再问，附推荐和理由。不讲语言、库、框架名词——不问“SQLite 还是 JSON”，问“数据多了以后，你要不要能按条件搜？”；模块、接口、注册表、分层这类架构词可以用，第一次带一句解释。不把一个方案当既定事实，也别把选项堆到五个。
  - 两种混在一起时，先让决策者定掉纯技术那部分，只把影响用户的点翻译了问。
- **涉及界面、观感、交互**：别问“你想要什么风格”，给 2–3 个小原型让他挑；说不清时请他扔**参照物**（截图、链接、现成产品）代替形容词。应用界面按 `vibe-apps`「界面：效果图先行」：HTML 效果图在浏览器里改到满意再照图实现，定稿的效果图算点过头的方向。
- **定稿后三行白话告知方向，然后直接开工，不等回复**（只在做过三点设计、多方案取舍或画了图时给）：**我要做什么 / 做完你会看到什么、怎么用 / 这次明确不做什么**，画了图的附上。能不能念给不懂代码的人听是判据。用户叫停就停下改方向。
- **必须停下来等用户**：新项目的架构方向尚未谈定且用户未委托 AI 决定时；或出现**此前没确认过**、会改变使用体验、数据影响或范围的选择时（照“会”那一支问）。已确认过的方向（包括在运行图、原型里点过头的）不再要点头。
