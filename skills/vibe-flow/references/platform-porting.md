# 平台按需适配

AI 宿主平台（Claude Code、Codex……）是 §5 里一条特殊的变化轴：平台按需增加，先只做正在用的那个；换到别的平台要用时，由那个平台的 AI 自己适配。本文件管三件事：出生时怎么把路留好、运行时什么时候主动开口、换平台时怎么适配。

**适用范围**：用到宿主能力的项目——hooks、skill / 插件清单、斜杠命令、指令文件、宿主的 shell 调用约定。只是被 AI 编写或调用的普通脚本不算。

**什么时候读**：新建这类项目时读第一节；已有项目这次确实要在另一个平台上用，读第三节并顺手补上它缺的平台约定。普通改功能、修 bug 不触发全项目补表。

## 一、出生时留路（首次交付前完成）

1. **共享判定放在平台无关的一处**：有判定逻辑的（判断拦不拦、算什么、生成什么），放进函数、模块或已有 CLI，不依赖任何平台的输入格式。各平台的壳只做三件事：把平台输入归一成判定要的参数、采集判定需要的上下文、把结果翻成平台认的格式。只有 skill、清单、指令文件这类纯声明的项目，没有判定可抽，不为此凭空造命令。
2. **各平台原生清单就是入口登记**：每个平台加载自己的清单（插件清单、hooks 定义文件……），没有统一选择或枚举平台的调用方时，不另造中央注册表。出现这样的调用方，再按 §5 一般变化轴的规矩收口。
3. **把平台约定说清楚，由收工 fork 写进蓝图**（`BLUEPRINT.md` 第 6 节，模板在 `living-blueprint/references/templates.md`）。主 agent 要在对话里把每个介入时机讲明白，fork 才有东西可写：
   - 主会话还是子任务；在什么动作之前或之后；判定需要哪些信息；
   - 判定不通过怎么办（拦下 / 只提示）；判定本身出错怎么办；
   - 拦截按回合还是按会话计数，被拦后再次触发怎么处理；
   - 平台缺这项能力时怎么降级，或者直接写「该平台不支持此能力」。
   行为必须能脱离平台术语读懂，不许只用某个平台的事件名来定义行为——另一个 AI 会找一个名字相近的事件，就当成行为等价。平台事件名、字段、配置位置属于适配映射，归 AGENTS.md 指向的实现处；确属对外 I/O 契约的名称照原样保留在蓝图里。
4. **验收平台无关**：有共享判定的，给它写平台无关的用例（喂输入 → 看结果和退出码）。纯声明的项目不搭测试框架，验证能加载、行为对即可。
5. **指路**：
   - `AGENTS.md`「约定」加一行：要在别的平台上用，读蓝图第 6 节，按 vibe-flow 的 `references/platform-porting.md` 第三节做；写明当前各平台的壳在哪。
   - **依赖宿主能力的 skill**，在 SKILL.md 里加一句运行时提醒（在别的项目里用这个插件时，AI 唯一看得到的就是 skill），写明三样：这个 skill 靠哪项宿主能力、平台状态表在哪（写随交付物一起分发、从 skill 目录找得到的路径，如插件仓的 `docs/BLUEPRINT.md`）、按第二节的规矩开口。例：

     > 本 skill 的 <某能力> 靠宿主的 <中性描述的时机> 实现。当前平台对这项能力的状态见 `<从 skill 目录可达的路径>` 第 6 节；这次要用的正好是它、而本平台对它不是「已支持」时，按 vibe-flow `references/platform-porting.md` 第二节提醒用户。

## 二、运行时主动开口

用户在某个平台上用一个插件或项目，**已被加载的入口**（skill、AGENTS.md 或别的说明）告诉你这次要用的能力依赖宿主时，查它的平台状态表，按本平台**这项能力**的状态说话，不看整个平台有没有打勾——部分适配也可能恰好缺这次要用的：

| 这项能力在本平台的状态 | 说什么 |
|---|---|
| 表里没有（本平台不在表里，或那行不含这项能力） | 表只列验证过的，表外只说明「还没有验证过的支持」。先只读查一下有没有写了一半的适配（源仓里本平台的壳、`HANDOFF.md`），再一句话问用户：没有 →「这个还没适配 <本平台>，要现在做吗？」；有 →「<本平台> 的适配做了一半 / 还没实测，要现在接着做吗？」。用户说做，才按第三节做（接着做的从 HANDOFF 续） |
| 已支持，但这次没生效（本机没启用、没信任） | 告诉用户怎么启用，不引导重做 |
| 降级 | 照表里写的降级表现告诉用户少了什么；要补全就按第三节做 |
| 找不到状态表 | 先在本次相关的范围里只读查（源仓的蓝图、AGENTS.md、各平台的壳），查清了按上面几行说；查不清才告诉用户不确定，不断定未适配 |

- 与这次要用的能力无关，一个字不提。
- 同一缺口本会话只问一次；用户已经明确要求适配的，视为同意，不再问。
- 盲区：没有任何入口被加载时（比如纯 hook、没有 skill 的插件装在未适配的平台上）无从发现，不为此补扫描机制；别的已加载入口碰巧发现了缺口，照样开口。

## 三、换平台适配

档位照 §2 / §7 正常判：首次接入常因影响面或关键未知落在好档，明确的小配置适配可以是省档。

1. **定位源仓**：用户多半是在别的项目里用这个插件时触发的。改动落在插件或工具的源仓，守源仓自己的规矩（开 worktree、提交分发流程等）；不改当前这个消费项目，也不改安装缓存。
2. **读约定和入口**：蓝图第 6 节（要什么、怎么降级），AGENTS.md（已有平台的壳在哪、怎么验证、踩过的坑）。
3. **查本平台现在的官方机制**：有哪些事件、能不能阻断、输入里有哪些字段、清单和配置放哪、要不要用户信任或启用，不凭记忆。本机已有实测回执（fixture、capture）优先用，但要核对平台版本和适用范围。
4. **写薄壳**：只做输入归一、上下文采集和结果翻译，不复制判定。非得改共享判定才能适配的，这是行为变化，不能藏在「适配」里：单列影响告诉用户，并回归已有平台。
5. **按顺序验证**：平台清单与分发 → 安装加载 → 必要的启用 / 信任 → 真实入口触发。只验本次新增或变更的时机；拦截类至少覆盖该放行、该拦下、拦下后能恢复三种情况，一条日志证明不了拦截生效。有共享判定的跑平台无关用例，壳的翻译层用实测抓到的平台输入作 fixture（公开仓先脱敏）。
6. **做不到实测**：没验证到的写进 `HANDOFF.md`（做到哪、还差哪种验证），状态表里不加这个平台（或不写这项能力）——表只列验证过的，下一个接手的从 HANDOFF 续，不重做。
7. **缺能力**：按约定写的降级做，并告诉用户少了什么；约定里没写怎么降级的，停下问用户，不许悄悄少一项。
8. **文档回填照 §8 交给收工 fork**：蓝图第 6 节的状态表、AGENTS.md 里本平台的壳和坑、CHANGELOG 一条（为什么这时候接入、缺了什么、怎么降级的）。
