# 收工派 fork 维护文档，与两个兜底钩子

`vibe-flow` §8 定了“文档跟着改才算完成，但不由干活的主 agent 来整理”；本文件放具体步骤。**什么时候读**：一批改动做完、验证过、交付汇报之前（微脚本只改头部契约行，免）；活没做完就要结束会话、需要写 `HANDOFF.md` 时；被文档闸拦下时。

## 1. 派 fork 的四步

1. **记下代码现状**：在项目里跑 `py -3 <vibe-flow skill 目录>/scripts/code_state.py`（非 Windows 用 `python3`），记住它打印的哈希。它只随非 `.md` 文件的内容变化：已跟踪文件的改动、暂存、删除，以及未跟踪文件的名字和内容。
2. **派一个继承本会话上下文的子 agent 维护文档**：Claude Code 用 Agent 工具、`subagent_type` 为 `fork`；Codex 用 `spawn_agent` 并继承全部历史。任务照写：「加载 living-blueprint，按它判断并更新本项目文档，覆盖这批改动的最终状态；只写这几份文档，不改代码、不生成别的文件；汇报不超过三行：改了哪些文件，或为什么这批不用记。」它继承了整段对话，意图和没选的路它都看得到，**不用另写简报**。活没做完要结束会话时，任务改成让它写 `HANDOFF.md`。
3. **等它完成再汇报或提交**：Claude Code 上派完就结束本轮，完成通知会唤醒你；Codex 上等子 agent 结束再收尾。等待期间不改代码；非改不可，改完回到第 1 步重来。
4. **核对回执**：再跑一次第 1 步的脚本，哈希不变才说明它没碰代码（`git status` 证明不了：原本就改过的文件被它再改，状态看起来一样）；变了就查清并撤回它对代码的改动。它说拿不准的意图，把答案补给它让它改（Claude Code 用 SendMessage 续接同一个 fork），主 agent 不自己动文档。它判断这批不用记、文档没动时，主 agent 照下面第 2 节写一条回执，否则文档闸会在下一次结束时再拦。

没有这类子 agent 可用时，主 agent 自己按 `living-blueprint` 改。

## 2. 文档闸（Stop 时，Claude Code 的 `hooks/doc_gate.py`、Codex 的 `hooks/doc_gate_codex.py`）

本轮改了 vibe 项目代码，而 `BLUEPRINT` / `CHANGELOG` 缺失、或两份都早于这批代码的最后一次修改，就拦一次，提示按上面四步派 fork。

- **被拦时如实判**：要记的就派 fork；纯内部改动、用户没感知过，就跑提示里那条回执命令（`doc_gate.py receipt --blueprint <路径> --reason "<一句话>"`），并在回复里说一句。别为过闸写假条目，也别写假回执。
- **回执**：一条管一对文档（同目录几个旁挂脚本各管各的），确认的是「这对文档管的全部代码在当前状态下都不用更新」，不只是本轮那几个文件。之后代码增删改、或这两份文档内容变了，回执自动失效、照常再拦；后台任务完成把你唤醒、代码没再变时不会重复拦。缺文档不能用回执，要先建；被 gitignore 的文件、超大的项目，回执验证不了，照常提醒。回执存在 `~/.vibe-flow/doc-receipts/`，Claude、Codex 两个闸和 session-sweep 都认。
- **它认得出的改动**：工具写入记录（Claude 的 Write / Edit，Codex 的 `apply_patch`），加上本轮写过或命令里写出路径的 git 仓库（会话目录所在仓库之外最多再扫几个）里本轮开始后改过、暂存或删掉的已跟踪文件和新建的代码文件——经 shell / Python 落盘的也算，本轮之前就有的改动不算。合并后删掉的 worktree，按对话里成功执行的 `git worktree add` 换回主仓路径判。
- **文档跟没跟上只看磁盘修改时间**（删掉的代码按所在目录的修改时间算），所以 fork 写的文档照样认。Claude Code 上还有后台子 agent 在跑时先不拦，等它完成、本轮再结束时重判；开发服务器这类 shell 后台任务不算。
- **可能多拦一次**：本轮之前就删掉、还没提交的文件，若本轮同一目录又有文件增删，会被算进本轮；命令里提到的别的仓库若有别的会话同时在改，也可能被算进来。如实说明后放行即可。
- **看不到的**：没在本轮写过、命令里也没出现过的仓库；Codex 其他 MCP 写文件工具；Codex 侧 shell 命令里的路径。没有触发闸不代表文档已经合格。
- Codex 的钩子随插件分发，无需改全局配置，但首次使用或定义变更后须在 Codex 中审阅并信任（CLI 用 `/hooks`）。

## 3. 压缩后读回（Claude Code 的 `hooks/compact_anchor.py`，SessionStart 且来源是压缩，手动、自动都算）

从对话记录里找本会话实际在做的项目，把它们 HANDOFF 的「已谈定」原文注入给你，有 `NEEDS.md` 就提示去读当前需求区（只有 NEEDS 也提示）。

- **注入全文的**：读或写过 HANDOFF / NEEDS、经 Write / Edit / esafe-code 写过文件、本会话为它开过 worktree 的项目，再加会话目录；最近在做的排前，最多几个。
- **只列路径的**：只读过、只在命令里提到的项目——当前任务属于它们时才去读，别把别的项目的约定套到当前任务。不开 worktree、只用 python 落盘的项目也只会列路径。
- 几个旁挂 HANDOFF 各自标明约束哪个脚本，只对照当前任务涉及的那份；区段太长时只列路径、要求读完，不截断。
- 收到这段就按 §4「读回」对照后再继续。它不拦压缩：HANDOFF 有没有改过，判断不了该记的有没有漏记。Codex 侧没有接，照 §4 文字执行。
