# 低耦合与变化轴：细则

`vibe-flow` §5 的底线和变化轴主规矩在 SKILL.md；本文件放展开的细则和交付前的结构自查。**什么时候读**（动手前，不是交付前）：本次要新增、去掉或替换某条变化轴的成员，或修改既有成员的能力，要收口成注册表，成员各自依赖外部东西，或本次引入、用到外部数据 / 默认运行策略（默认模型、端点、价格配额）时。公司固件 / 产品代码按该仓库规范，不套本文件。

具体到代码长什么样，由 `vibe-scripts` / `vibe-apps` 各自给模板；这里只定规矩，不绑语言。

## 1. 外部数据和默认运行策略

需要独立于实现去调整的值——默认用哪个模型、部署端点 / URL、外部价格与配额这类——集中定义在一处：标准级以上放配置文件，微脚本可以是文件头部一块具名常量区。由入口（`main()`、CLI、应用启动处）读取、校验，再作参数显式传给逻辑；逻辑模块不自己去读配置，也不在别处另写一份默认值。

- **哪些不算**：属于实现契约的协议版本、数据格式版本、算法固有阈值不在此列；但“支持 v1 / v2”是能力，“默认选 v2”仍是运行策略。
- **能力与选择分开**：适配器声明“这个成员接受哪些值”是它自身的能力，留在适配器；“这次默认用哪个”是运行策略，进配置。同一个 `"max"`，在适配器的可选值清单里是能力，在默认值里是策略。
- **不许未声明的回退**：配置读不了或写坏时，按事先写明的契约处理。决定行为、成本或目标的必需配置（用哪个模型、发到哪个地址）出错就明确报错，停下受影响的那个操作；可选配置（如外观主题）可以按契约告警后用默认。不许悄悄换成别的模型、目标或处理策略。局部配置出错只停受影响的操作，其余照常——成员级的按下面「故障隔离」处理；全局必需的配置失效，或操作本身要求全有全无时，才整体失败。
- **只是换值不建注册表**：问出来的若是“这个值以后会被换掉”（新模型、新地址），只是替换取值、处理方式不变时，按本节收进配置；换过去之后调用方式或能力也跟着不同，才按变化轴判断。

## 2. 变化轴

- **认轴**：写代码前问一句“这里以后会不会再来一个同类的，或者去掉一个？”会，就记成一条轴（好档写进 §4 三点设计的“变化轴”那行；省档心里过一遍）。**认轴只是记下来，动作按实际成员数触发**，不按想象中的未来预建任何东西。
- **只有一个实际成员**：不建注册表、不建目录、不抽接口（YAGNI），只要求这个成员的代码聚在一处，不散进别处——给第二个成员留好搬家路。
- **什么算成员**：工具正式提供的可选运行方式才算——比如用户能选“真实设备 / 仿真设备”，仿真就是第二个成员。只在测试里临时传进去的假函数、假对象是**测试替身**，不算成员，不进运行时注册表；“要测试”本身不是建接口和注册表的理由（逻辑与 IO 分开后，测试直接喂数据就行）。
- **出现第二个实际成员，或调用方第一次出现成员名单 / 按成员名分支**：必须先收口成“一份注册表 ＋ 每成员一个适配器”，再加行为。这次收口是本次改动的一部分，不算顺手重构；不许在没收口的状态下复制第二份分支。
- **适配器按体量缩放**：标准级单文件脚本里，注册表是一张 dict，适配器可以只是一个函数或一条数据记录；只有工具包级才要求每成员一个文件。
- **唯一权威来源**：运行时的成员清单和成员特有的能力只有注册表这一处；调用方（CLI 选项、循环、校验、界面）一律从注册表派生，不另写名单，不按成员名分支（`if 成员 in (a, b)`、`成员 == a`）。按能力分支就让适配器自己声明能力，调用方去问适配器。测试、文档、示例配置、兼容迁移、用户可见的输出里出现成员名是正常的，不算违规。
- **收好之后的验收句**：加或去掉一个成员，只动它自己的适配器和注册表。做了下一条故障隔离的，再加半句“一个成员出错只影响它自己”。有 `BLUEPRINT.md` 的，把这句写进第 4 节硬约束。
- **故障隔离（只在成员各有外部依赖时要求）**：成员各自依赖第三方库、设备、网络、外部配置或文件时，一个坏了（依赖没装、配置缺失、导入失败），聚合类命令（状态检查、批量注册、全部同步）把它记成“不可用 ＋ 原因”，继续处理其余成员，最后按汇总结果定退出码；注册表只登记名字、惰性加载成员，不许因为一个成员加载失败而整体起不来。用户点名要这个坏成员，或操作本身要求全有全无时，明确失败并返回非零，不许静默部分成功。成员只是几个纯函数（比如两种格式转换）时，一张 dict 就够，不需要这套。
- **AI 宿主平台**是一条特殊的轴：各平台的原生清单就是入口登记，没有统一选择或枚举平台的调用方时不另造中央注册表；有共享判定就放在平台无关的一处，各平台的壳只做翻译。细则见 `platform-porting.md`。
- **存量代码已经散了**（名单写死在多处）：本次改动正要增删这条轴的成员或改它的能力时，收口算本次功能的相关改动，照上面“第二个成员”那条办；收口范围明显超出本次改动（牵连很多文件）时先停下，说清散在几处，让用户选先收口还是先打补丁。本次没碰的其他轴只报告，不动。

## 3. 交付前的结构自查

- **所有档 · 拔插自查**：本次动到的每条变化轴，交付前搜一遍调用方里有没有另写的成员名单、`if 成员 in (...)`、`成员 == ...` 这类按名特判；有就是没收好，改完再交。测试、文档、配置、输出里出现成员名不算。
- **所有档 · 配置取值自查**（本次引入或用到了第 1 节的值时）：① 列出本次涉及的实际值和它们的配置字段；② 在实现和测试里搜这些值的使用处；③ 逐处判断是否形成了第二份运行默认值或选择逻辑——形成了就是没收好。搜到字面量只是候选，不等于违规：微脚本的头部常量区、适配器的能力声明、专门验证发布默认值或兼容契约的测试都可以出现真实值；普通的参数传递和命令组装测试用注入的假值。不要让所有预期值都从生产配置读——配置被误改时，实际值和预期会一起变，测试照样通过。验收：经真实的配置加载路径换一个测试值，最终调用跟着变；必需配置写坏时，受影响操作的外部调用不发生。
- **好档 · 结构测试**（本次新建或收口了变化轴）：① 调用方的成员清单和能力确实从注册表派生（往注册表加一个假成员，调用方能看到它）；② 成员各有外部依赖、做了故障隔离的，再模拟一个成员加载失败，确认其余成员和聚合命令照常工作。规矩写在文档里拦不住漂移，测试能拦。
