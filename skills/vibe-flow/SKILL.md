# Vibe Flow：轻量 vibe-coding 主流程

## 核心原则

> 先明确需求，再判这是小事还是大事：**小事要省，大事要好。**

省的是流程，不是质量；好的是该厚的地方厚，不是每次走满。本 skill 是这套工作流的**总入口与档位闸门**：`vibe-scripts` / `vibe-apps` / `clarify-needs` 都先经过这里判档再进。跨分支的规矩（低耦合 §5、文档 §6、谁拍板 §4）以本 skill 及其 `references/` 为唯一权威出处，分支 skill 只给代码例子；不把各 skill 串成必经关卡。

**细则按时机读，不预读**（路径相对本 skill 目录）：

| 时机 | 读 |
|---|---|
| 本次要增、删、换变化轴的成员或改既有成员的能力，要收口成注册表，成员各有外部依赖，或引入 / 用到外部数据和默认运行策略（默认模型、端点、价格）——动手前读 | `references/low-coupling.md` |
| 一批改动做完、交付汇报之前（微脚本免）；活没做完要结束会话；被文档闸拦下 | `references/doc-fork.md` |
| 新建用到宿主能力（hooks、插件清单、斜杠命令）的项目，或本次要在另一个平台上用 | `references/platform-porting.md` |
| 好档要画「我打算怎么搭」图 | `clarify-needs` 的 `references/run-model.md` |

## 整套工作流总图

一次判档，全流程沿用同一档。**不命中的环节完全不提**——这张图是路由图，不是阶段清单。

| 环节 | 省档（默认） | 好档 | 用什么 |
|---|---|---|---|
| 判意图 | 都要 | 都要 | §1 |
| 判档 | 都要（一次） | 都要（一次） | §2 |
| 开工前 | 查自己有没有现成的 | ＋查市面有没有 | §3、`script-manager` / `scan-field` |
| 明确需求 | 不澄清，或只问一个问题 | 挖目标 / 分清偏好与约束 / 翻译验收；有流程的画「它跑起来是什么样」图 | §4、`clarify-needs` |
| 探方案 | 不探，直接做 | 技术取舍 AI 定、决策者审；影响用户的翻译成后果再问；界面类出原型；多模块的画「我打算怎么搭」图；定稿后白话告知方向即开工 | §4 |
| 实现 | 最小可用；守低耦合底线，不预建插口 | 按分支的完整纪律；变化轴列进三点设计 | §5、`vibe-scripts` / `vibe-apps` |
| 留文档 | 按工具寿命，不按档（§6）；收工派 fork 维护；干活时只往 HANDOFF「已谈定」区记谈定的事 | 同左；需求仍演化时＋`NEEDS.md` | §4、§6、§8 |
| 外援 | 不咨询；机械活照样甩给 opencode | 实质取舍咨询决策者(claude↔codex)，机械活甩给 opencode | §7、`ai-room` |
| 验证 | 代表性输入跑通 ＋ 拔插自查；给别人的按交付形态跑 | 按交付形态实际使用 ＋ 针对性测试 ＋ 结构测试 | §8 |
| 收工后 | 无 | 膨胀了剪枝 / 完工了扫同款 | §9、`cut-scope` / `scan-field` |

## 1. 先判断用户此刻要什么

| 请求 | 动作 |
|---|---|
| 可行性、解释、比较、只读诊断 | 先直接回答；不要擅自转成建项目或改文件 |
| 明确要求构建、修改或修复 | 进入后续流程并完成实现与验证 |
| “可以 / 继续 / 按这个做”且方案已经谈定 | 视为继续实现，不再重复索要批准 |

回答“能不能实现”时，先给结论和关键限制。只有用户要求继续做，或上下文已经明确授权改动，才进入实现。

## 2. 判档（承重环节，判一次）

判两件互不相干的事，别混：

| 维度 | 看什么 | 决定什么 |
|---|---|---|
| **档位**（流程厚度） | **本次改动**本身 | 澄清几轮、探不探方案、叫不叫决策者、验证多厚 |
| **产物要求** | **工具寿命和去向** | 要不要文档（§6）、要不要按交付形态验证（§8） |

**一个长期工具上的明确小改，档位是省档**——项目活多久不让这次改动变厚；它只决定文档要跟着改。

### 档位：默认省档，升档要理由

**升到好档必须说得出命中哪条，并在回复里说一句。** 判据只看本次改动，命中任一即好档：

- **范围或影响面大**：新加一整块功能、牵连很多文件、要新建的工具本身就复杂（多个模块、多种输入输出）；或改动虽小但影响面广——单位换算、统计口径、共享数据的写入，一错就影响全部数据。**“新建”本身不升档**：需求清楚的小脚本，新写也是省档。
- **出错后果重 / 不可逆**：删除、覆盖、迁移数据，联网上传，发出去收不回；或错了会污染已有数据、很难发现。
- **关键未知**：有会实质改变行为、数据或方案的未知。普通实现细节拿不准不算，那是 AI 自己查、自己定的。
- **多目标纠缠**：两个以上独立目标或独立用户搅在一起。

**拿不准就按好档·轻走。** 省档只给一眼看得出的明确小改：范围小、可逆、目标清楚。某条判据命没命中说不清，就按好档·轻（§7）走，并说一句「拿不准，按好档走」——用户自己判断不了档位，判低了他发现不了；判高了代价看得见，他一句「按小事做」就降回来。「重」仍只在明确命中「出错后果重 / 不可逆」时用。

这几条**都能在不深挖需求的情况下粗判**——先粗判，按档澄清，澄清中发现事实变了就升档（只升不降，并说明原因）。唯一的例外：因为拿不准才升上来的，澄清后确认就是明确小改，可以降回省档，同样说一句。**「以后还会用」「要给别人」「一次做不完」都不是升档理由**：前两个归产物要求，最后一个由 `HANDOFF.md` 承接（§6）。

**用户一句话直接定档，优先于以上判据。** 听到“这个随便做一下 / 按小事做”→ 省档；“这个要做好 / 好好想想”→ 好档。此时不要再自行推翻，也不要反问判据。

### 产物要求：看工具寿命和去向

- **会再用**（不是跑完即弃）→ 文档按 §6（微脚本仍然只用头部契约行）。
- **给别人**（分发 exe / 仓库 / 插件，或别人会依赖它）→ 验证按交付形态做（§8：构建后实际运行该产物）。
- 两者都不改变档位。

## 3. 开工前：先看有没有现成的

- **自己有没有（两档都做）**：要写独立脚本或小工具前，先查 `script-manager` 的 `INDEX.md`（装了才有），能复用就别重造；已有脚本改一点就够用时改它，不新建。
- **市面有没有**：查完仍要新建或重写，且做的东西**能拿出去**（插件 / 工具包 / 产品 / 会长期活的工具），或打算重写替换一个已有的东西 → 交给 `scan-field` 的**开口那头**（几分钟、不落文档）。日常改功能、加子命令、修 bug、一次性微脚本**不扫，一个字都不提**。

## 4. 明确需求，必要时再探方案

先检查三件事：用户真正想得到的可见结果是什么？他说的是目标、偏好、建议方案，还是不可违反的硬约束？哪些缺失信息会让最终行为、数据、成本或范围明显不同？

**只澄清会改变结果的内容**，按档决定厚度：

- **省档**：清楚且小、可逆 → 直接实现。结果或约束不清楚 → 只问最少的一个具体问题，得到答案就继续。
- **好档**：把目标 / 偏好 / 约束 / 验收分开——目标缺失就先问“你拿这东西最终想达成什么”；“最好别用 X”“越小越好”先分清是硬约束还是偏好；“简单 / 好看 / 稳定”翻成几条看得见的标准。
- **需求严重纠缠**（多个独立目标、需求持续膨胀、方案与约束混作一层）：**直接起 `clarify-needs`**，起之前说一句为什么要多问这一轮。用户说“别问了直接做”就立刻收，退回只问最少的一个问题。省档微任务不起它。

### 探方案（只在好档）

- **只有一条明显路**：不比方案，直接做（满足下面画图条件时照画）。
- **涉及数据模型、持久化、主要 UI 流程、模块边界或分发方式**：三点短设计“怎么做 / 为什么 / v1 明确不做什么”，**再加一行“变化轴”**：以后会增、删、换的是哪几类东西，各自现在有几个成员（§5）。没有写“无”，不许省掉这一行。
- **「我打算怎么搭」图**：好档，且**本次动到**至少两个职责模块、或数据要跨好几个处理 / 存储环节时默认画（按本次实际动到的算，与有没有多条路无关）。画模块怎么分、各管什么、数据怎么流、存在哪，配一两句为什么，随三行白话一起给用户——他懂架构层、不懂代码，藏起来他就没法及时插话。**图是告知不是审批**，给完直接开工；内部疑点 AI 自己处理（§7），只有此前没确认过、会改变使用体验或数据的点才标 `guess` 并问。用户看图后开口：要改的照改，提问的先解释为什么这么搭，给建议的先判断采不采纳并说理由，别把一句“为什么不这样”当成改动命令。画法见 `run-model.md`（`--layer build`）。
- **确实有 2–3 条各有取舍的路**：先问一句——**选 A 和选 B，用户用起来会不会不一样？**
  - **不会**（库、代码怎么分、内部数据结构）：AI 自己定，不问用户；好档按 §7 交决策者审，审完自己拍板。
  - **会**（快慢、能不能离线、会不会删改用户数据、多花多少时间、以后能不能加同类的东西）：把每条路**翻译成用户能感知的后果**再问，附推荐和理由。不讲语言、库、框架名词——不问“SQLite 还是 JSON”，问“数据多了以后，你要不要能按条件搜？”；模块、接口、注册表、分层这类架构词可以用，第一次带一句解释。不把一个方案当既定事实，也别把选项堆到五个。
  - 两种混在一起时，先让决策者定掉纯技术那部分，只把影响用户的点翻译了问。
- **涉及界面、观感、交互**：别问“你想要什么风格”，给 2–3 个小原型让他挑；说不清时请他扔**参照物**（截图、链接、现成产品）代替形容词。
- **定稿后三行白话告知方向，然后直接开工，不等回复**（只在做过三点设计、多方案取舍或画了图时给）：**我要做什么 / 做完你会看到什么、怎么用 / 这次明确不做什么**，画了图的附上。能不能念给不懂代码的人听是判据。用户叫停就停下改方向。
- **必须停下来等用户**：只有出现**此前没确认过**、会改变使用体验、数据影响或范围的选择时（照“会”那一支问）。已确认过的方向（包括在运行图、原型里点过头的）不再要点头。
- 想要完整的 brainstorming → 计划落盘 → 按计划执行，手动调 `superpowers-manual`；本流程不依赖它。

### 用户与 AI 的决策边界

用户决定：目标、可见行为、范围和优先级；时间 / 成本取舍；删除、覆盖、迁移、联网、隐私等数据影响；会改变产品含义的取舍。

AI 决定并说明：库、模块划分、文件名、内部 API（模块和数据流属于架构层，按上面的条件画图给用户看）；普通实现细节和测试工具；不改变用户体验的可逆技术选择。

纯技术内部选择不许反问用户；拿不准就交给决策者（§7），不是交给用户。要用户拍板的点，一律先翻译成后果再问——用户决定“要什么”，不是“怎么做”。

### 谈定就记下来，动手前读回（不分档）

讨论里定下的东西从谈定到收工只活在对话里：一压缩就丢细节，丢的常是最早、最根本的那句；来回纠正时又容易只盯最新一句。所以谈定当场记，动手前读回。**只记不读等于没记。**

- **记什么**：用户第一次明确说出的核心目标和硬约束（一出现就记）；用户对具体做法点头，或纠正了你的理解；决策者审完你采纳或否决的结论（写“采纳 codex 建议：……”，没采纳的不写成约束）。没谈出结论的、纯技术又没经审的细节不记；已写进 `NEEDS.md` 当前需求区的不重复。
- **记在哪**：`HANDOFF.md` 的「已谈定」区，放最前，标签只能写 `**已谈定**：` 或 `## 已谈定`（压缩后读回的钩子只认这两种）。位置按 §6（项目 `docs/HANDOFF.md`，旁挂 `<脚本名>.HANDOFF.md`）；还没有就建一份只含这一区的。微脚本要跨会话接着聊也可以建旁挂的，不连带整套文档、不升档；做完由主 agent 把仍要守的约定并进头部契约行，再删掉它。
- **怎么记**：一事一条，单独能看懂，不写“按上面的方案”：`日期 · 来源 · 事项：当前结论；排除的做法及理由（如有）`，来源写“用户”或“采纳 codex 建议”。补充条件合进原条，不另起一条只留最新一句；明确推翻才改写，被推翻的做法删掉，仍有效的否决理由留在“排除”里。
- **谁记**：干活的主 agent 当场记，一条一两行；只动这一区，不为此加载 `living-blueprint`、不整理别的文档。只读或没有写权限时，在回复末尾列出待记的条目。
- **读回**：接手、恢复会话或压缩之后，先读「已谈定」区（和 `NEEDS.md` 当前需求区，有的话）。每次据此调整方案或开始实施之前，对照原始目标和全部仍有效的条件——本轮没再提到，不等于取消了。用户最新的明确指示可以更新旧约定（改写那一条）；当前有效约定优先于压缩摘要。
- **偏离信号**：用户指出之前说过的条件被漏了或理解错了（“我说了……”“我当时不是说……”“你理解错了”），或你发现当前方案和「已谈定」冲突——立即读回全部有效约定，按整体修正，不只改最新一句，并把漏掉的条件补进去。明确的纠正直接执行，不让用户把说清的再点一遍头；只有仍有歧义或约定互相冲突时，才问那一个具体问题。

## 5. 选择实现分支

| 场景 | 路由 |
|---|---|
| 独立 Python 命令行脚本、小工具、自动化 | 加载 `vibe-scripts` |
| 有界面、要打包分发、可能成长为网站的个人 Python 应用 | 加载 `vibe-apps` |
| 公司固件、产品代码、构建系统或已有正式仓库 | 遵守该仓库规范；不要套个人工具技术栈 |
| 不属于以上类型 | 沿用项目现有结构，以最小改动完成 |

两个 vibe-* skill 内部各有自己的分级（微 / 标准 / 工具包），**按代码本身定级**，与档位无关。

### 低耦合底线与可插拔（所有档、所有脚本和应用）

低耦合是底线，不是好档的加分项；档位只决定做到多厚。公司固件 / 产品代码按该仓库规范，不套这一节。

- **逻辑与 IO / 界面分开**：算东西的函数不读写文件、不打印、不碰网络和设备，输入显式传进来、结果返回出去。微脚本做到“纯函数 ＋ `main()`”就够。
- **依赖单向**：外层（命令行、界面、适配器）调逻辑，逻辑不知道外层存在。不靠全局状态串模块，要用的东西作参数传进来。
- **外部数据和默认运行策略集中一处**：默认模型、端点 / URL、外部价格与配额这类值，标准级以上放配置文件、微脚本放头部具名常量区；入口读取校验后传参，逻辑不自己读配置、不另写默认值。必需配置出错就明确报错、停下受影响的操作，不许悄悄回退。哪些不算、能力与选择怎么分 → `low-coupling.md`。
- **变化轴**（以后会增、删、换的那类东西：平台、厂商、格式、数据源、输出目标、存储后端）：写代码前问一句“这里以后会不会再来一个同类的，或者去掉一个？”。**只有一个实际成员**：不建注册表、不抽接口，只要求它的代码聚在一处。**出现第二个实际成员，或调用方开始按成员名单 / 成员名分支**：先收口成“一份注册表 ＋ 每成员一个适配器”再加行为，收口算本次改动。验收：加或去掉一个成员，只动它自己的适配器和注册表。测试替身不算成员。什么算成员、适配器体量、唯一权威来源、故障隔离、存量已经散了怎么办 → `low-coupling.md`。
- **AI 宿主平台**（Claude Code、Codex……）按需适配：先只做正在用的平台，首次交付前把路留好，换平台时由那个平台的 AI 自己适配 → `platform-porting.md`。只是被 AI 编写或调用的普通脚本不算。

## 6. 留文档（按工具寿命，不按档位）

本节只管**哪些项目要哪些文件、放哪**，是这件事的唯一权威出处；每份文件写什么、什么时候更新，归 `living-blueprint`。

| 项目 | 要带的文件 |
|---|---|
| **微脚本**（定义以 `vibe-scripts` 定级表为准：<100 行、单一功能、IO 形式单一） | 只有脚本头部的契约行（结构 / 用途 / 用法 / 原始需求），不另建文档 |
| **和别的脚本共处一个目录的单文件脚本** | 同名旁挂 `<脚本名>.BLUEPRINT.md` ＋ `<脚本名>.CHANGELOG.md`；有没做完的活时再加 `<脚本名>.HANDOFF.md`。头部 `结构:` 行代替 AGENTS.md |
| **独占一个目录的项目**（不管是单文件脚本、工具包还是应用） | 项目根 `AGENTS.md` ＋ `docs/BLUEPRINT.md` ＋ `docs/CHANGELOG.md`；有没做完的活时再加 `docs/HANDOFF.md` |
| 好档、需求仍在演化 | 另加 `docs/NEEDS.md`（归 `clarify-needs`） |
| 公司固件 / 产品代码 | 按该仓库规范，不套本节 |

- 分界按**目录归属**，不按代码大小：独占目录就有 AGENTS.md，和别的脚本挤在一起就用旁挂文件。
- `HANDOFF.md` 只在有没做完的活时存在，做完删掉——没有这个文件就表示没有进行中的工作。讨论阶段谈定了东西、还没开工时，也可以先有一份只含「已谈定」区的（§4）。
- **同一件事的进度只记一处**：进度和交接只写 HANDOFF，不写进 pstate 条目，也不写进平台原生记忆或 hub 金库（记忆只存长期结论和教训，看到进度类条目就以 git log 和 HANDOFF 为准，删掉或改成指针）。pstate（project-state 插件）管的是另外两件：**会话互斥**（哪个会话正在干哪件事、占着哪些文件，撞上由钩子拦下）和**待办条目**（一行标题 + 状态 + 一句目标 + HANDOFF 路径）；看板上已有的事，开工前先 `claim`。公司仓不建 vibe 文档，也不加锁、不新建 pstate 条目。session-sweep 只是发现入口：从它那里捡起一件事，进度落回 HANDOFF，不在它那里维护。
- 项目级只建 AGENTS.md，两个平台读同一份；只有当前环境的 Claude Code 确实不读 AGENTS.md 时，才加一个内容只有一行 `@AGENTS.md` 的 CLAUDE.md。

文档是连续工作的记忆，不是开工许可证。不要同时生成一套重复的需求、设计、计划文档。

## 7. 必要时才用 ai-room 叫外援

角色固定：**claude 和 codex 是决策者（你是 claude 就问 codex，反之亦然），opencode 只当执行者。** 怎么调用、上下文怎么给、超时怎么续，全归 `ai-room` skill，本节只管**什么时候叫、审多少**。

- **咨询决策者**：需求已经清楚、且仍有一个会实质影响架构、可维护性或迁移成本的技术取舍，才叫。交的是**你自己的方案**让它挑毛病，一次一个具体问题。决定要叫就直接派，不反问用户。
- **派执行者**：没有技术取舍的机械活（批量替换、格式化、补样板、跑测试摘失败……）直接派。有取舍的，先让决策者把方案定下来再拆成任务派；方案审过一次，拆出来的任务不必每件重审。
- 决策者说“需要用户拍板”时，只有真跨过 §4 用户决策边界才去问用户，否则自己定。
- 审完采纳或否决了什么，按 §4 当场记一条。台账只记问了什么，不记结论。

| 情形 | 咨询密度 | 能不能派 opencode |
|---|---|---|
| **机械活**（无技术取舍） | **不咨询** | 随便派，鼓励派 |
| **省档** | 不叫外援 | 实现里的机械部分照样派 |
| **好档 · 轻**（升档理由是「范围或影响面大」「关键未知」「多目标纠缠」） | **只审方案**：开工前咨询一次，之后冒出**新的**实质取舍才再咨询 | 方案定稿后拆任务派 |
| **好档 · 重**（命中「出错后果重 / 不可逆」，或要给别人且本次改动范围大） | **方案审 ＋ 关键步骤结果审**：关键步骤做完送回决策者过一眼；机械步骤不逐个审 | 同上，逐步派 |

「重」不是第三个档位，是好档内部按已有判据再分；判档仍然只判一次。

**停止条件**：同一个问题不二次送审；决策者说通过就往下走；连续两步没有新问题就停止回审，剩下的自己复核。执行者的产出一律自己复核——它是执行者不是负责人。

## 8. 实现与验证

实现时始终保持轻量：先交付最小但完整、可实际使用的一条行为链；保留已有行为、规则和用户写下的意图，不为简化或解决冲突而静默删除——遇到会改变行为的冲突，指出来等用户决定；不默认要求 TDD、正式计划、工作树或子代理，仅在好档中风险确实高、或用户明确要求时单独采用（收工派 fork 不在此列）；修改范围与授权一致，不顺手重构无关代码。

**所有档都必须做一次与交付形态相符的实际使用检查**——只跑单测、不跑用户真实入口不算。此外按档追加：

- **省档**：用代表性输入跑通即可，不为测试形式本身搭框架。
- **好档**：数据转换、持久化、迁移、已知回归、边界组合，增加针对性自动化测试；UI 要启动并走通核心用户路径；要可分发产物，就构建后运行该产物。
- **公司固件 / 产品代码**：遵守仓库规定的编译、静态检查、测试、真机或协议验证。无法执行的验证要明确说明，不能把“看起来正确”写成“已完成”。

**结构也要验**（个人脚本和应用）：所有档交付前做**拔插自查**——本次动到的变化轴，调用方里有没有另写的成员名单或按成员名特判；动到外部数据 / 默认运行策略的再做**配置取值自查**；好档新建或收口了变化轴的补**结构测试**。后两项的做法见 `low-coupling.md` 第 3 节。

**文档跟着改才算完成，但不由干活的主 agent 来整理**——全压在主 agent 上下文里会拖累正事。干活期间不加载 `living-blueprint`、不整理 `BLUEPRINT` / `CHANGELOG` / `AGENTS.md` / `HANDOFF`，只做 §4 的即时记录；例外是 vibe-apps 脚手架里 `AGENTS.md` 的架构约束段，由实现者随目录创建。`DESIGN.md` 归 vibe-apps；`NEEDS.md` 的需求梳理归 `clarify-needs`。一批改动做完、验证过、交付汇报之前（微脚本只改头部契约行，免），**派一个继承本会话上下文的 fork 维护文档，等它完成、核对它没碰代码再汇报**——四步照 `references/doc-fork.md` 做。活没做完要结束会话时，同样派 fork 写 `HANDOFF.md`。没有这类子 agent 可用时，主 agent 自己按 `living-blueprint` 改。

**两个兜底钩子**（细则同在 `doc-fork.md`）：
- **文档闸**（Stop 时，Claude Code 和 Codex 都有；Codex 上首次使用或钩子定义变更后，须先在 Codex 中审阅并信任钩子，CLI 用 `/hooks`，否则它不执行）：被拦就派 fork；纯内部改动就跑提示里那条回执命令写明理由（fork 判断不用记、文档没动时也写），别为过闸写假条目或假回执。没有触发闸不代表文档已经合格。
- **压缩后读回**（只在 Claude Code）：收到注入的「已谈定」原文或待读路径，就按 §4「读回」对照后再继续；只列了路径的项目，当前任务属于它才去读。

完成时简洁报告：

1. 交付了什么；
2. 实际验证了什么（含拔插自查结果）；
3. 文档改了什么（fork 的回执，微脚本免）；活没做完就收尾时，`HANDOFF.md` 已更新到能让零上下文的接手者直接开工；整件事做完时，`HANDOFF.md` 已删；
4. 哪些高风险项尚未验证。

## 9. 收工之后（只在命中时提一句，不是收尾仪式）

省档做完就结束，什么都不提。好档在命中下列情形时，**用一句话告诉用户有这个动作可用**，用户要才做：

| 命中情形 | 可用动作 |
|---|---|
| 迭代多轮、开始觉得“这块是不是不用做” | `cut-scope` 剪枝（只读，只给方向） |
| 做到能用了，想知道生态位和能抄的点 | `scan-field` 的**回头那头**（产原创度对比 + 升级方向文档） |
| 这轮做的正好是 skill / 插件本身 | `skill-review` 复盘（在 xu-skills 插件） |
