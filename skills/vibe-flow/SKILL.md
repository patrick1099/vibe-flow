# Vibe Flow：轻量 vibe-coding 主流程

## 核心原则

先明确需求，再判本次改动：**小事要省，大事要好。** 本入口只负责公共闸和路由；不命中的阶段不提、不预读子 skill。公共规则以本文及其 references 为唯一出处，分支只给适用栈的落法。

直接服务用户时先读本文；已分派的监工、实现、验证、文档角色按 [references/role-reading.md](references/role-reading.md) 的明确清单读取，不要求通读父入口，也不重新做已完成的决策。

**细则按时机读**（角色只读当前职责命中的项）：

| 时机 | 读 |
|---|---|
| 新项目架构讨论；已定架构需要改变；好档探方案 | [references/planning.md](references/planning.md) 的对应部分 |
| 增删换变化轴成员、改成员能力、收口注册表、成员各有外部依赖，或用到外部数据/默认运行策略，动手前 | [references/low-coupling.md](references/low-coupling.md) |
| 已定多任务计划委托监工；监工接任 | [references/batch-supervisor.md](references/batch-supervisor.md) |
| 委派、实质技术取舍或关键结果复核 | [references/collaboration.md](references/collaboration.md) |
| 改动完成且验证过、交付前；未完要结束会话；被文档闸拦下（微脚本免） | [references/doc-fork.md](references/doc-fork.md) |
| 新建用到宿主能力的项目，或换宿主平台 | [references/platform-porting.md](references/platform-porting.md) |
| 要画用户运行模型或好档搭建图，画之前 | [run-model.md](../clarify-needs/references/run-model.md) |

## 1. 先判断用户此刻要什么

| 请求 | 动作 |
|---|---|
| 可行性、解释、比较、只读诊断 | 先直接回答；不要擅自转成建项目或改文件 |
| 明确要求构建、修改或修复 | 进入后续流程并完成实现与验证 |
| “可以 / 继续 / 按这个做”且方案已经谈定 | 视为继续实现，不再重复索要批准 |

回答“能不能实现”时，先给结论和关键限制。只有用户要求继续做，或上下文已经明确授权改动，才进入实现。

## 2. 判档（承重环节，判一次）

判两件互不相干的事，别混：

| 维度 | 看什么 | 决定什么 |
|---|---|---|
| **档位**（流程厚度） | **本次改动**本身 | 澄清几轮、探不探方案、叫不叫决策者、验证多厚 |
| **产物要求** | **工具寿命和去向** | 要不要文档（§6）、要不要按交付形态验证（§8） |

**一个长期工具上的明确小改，档位是省档**——项目活多久不让这次改动变厚；它只决定文档要跟着改。

### 档位：默认省档，升档要理由

**升到好档必须说得出命中哪条，并在回复里说一句。** 判据只看本次改动，命中任一即好档：

- **范围或影响面大**：新加一整块功能、牵连很多文件、要新建的工具本身就复杂（多个模块、多种输入输出）；或改动虽小但影响面广——单位换算、统计口径、共享数据的写入，一错就影响全部数据。**“新建”本身不升档**：需求清楚的小脚本，新写也是省档。
- **出错后果重 / 不可逆**：删除、覆盖、迁移数据，联网上传，发出去收不回；或错了会污染已有数据、很难发现。
- **关键未知**：有会实质改变行为、数据或方案的未知。普通实现细节拿不准不算，那是 AI 自己查、自己定的。
- **多目标纠缠**：两个以上独立目标或独立用户搅在一起。

**拿不准就按好档·轻走。** 省档只给一眼看得出的明确小改：范围小、可逆、目标清楚。某条判据命没命中说不清，就按好档·轻（§7）走，并说一句「拿不准，按好档走」——用户自己判断不了档位，判低了他发现不了；判高了代价看得见，他一句「按小事做」就降回来。「重」仍只在明确命中「出错后果重 / 不可逆」时用。

这几条**都能在不深挖需求的情况下粗判**——先粗判，按档澄清，澄清中发现事实变了就升档（只升不降，并说明原因）。唯一的例外：因为拿不准才升上来的，澄清后确认就是明确小改，可以降回省档，同样说一句。**「以后还会用」「要给别人」「一次做不完」都不是升档理由**：前两个归产物要求，最后一个由 `HANDOFF.md` 承接（§6）。

**用户一句话直接定档，优先于以上判据。** 听到“这个随便做一下 / 按小事做”→ 省档；“这个要做好 / 好好想想”→ 好档。此时不要再自行推翻，也不要反问判据。

### 产物要求：看工具寿命和去向

- **会再用**（不是跑完即弃）→ 文档按 §6（微脚本仍然只用头部契约行）。
- **给别人**（分发 exe / 仓库 / 插件，或别人会依赖它）→ 验证按交付形态做（§8：构建后实际运行该产物）。
- 两者都不改变档位。

## 3. 开工前：先看有没有现成的

- **自己有没有（两档都做）**：要写独立脚本或小工具前，先查 `script-manager` 的 `INDEX.md`（装了才有），能复用就别重造；已有脚本改一点就够用时改它，不新建。
- **市面有没有**：查完仍要新建或重写，且做的东西**能拿出去**（插件 / 工具包 / 产品 / 会长期活的工具），或打算重写替换一个已有的东西 → 交给 `scan-field` 的**开口那头**（几分钟、不落文档）。日常改功能、加子命令、修 bug、一次性微脚本**不扫，一个字都不提**。

## 4. 明确需求，必要时再探方案

先检查三件事：用户真正想得到的可见结果是什么？他说的是目标、偏好、建议方案，还是不可违反的硬约束？哪些缺失信息会让最终行为、数据、成本或范围明显不同？

**只澄清会改变结果的内容**，按档决定厚度：

- **省档**：清楚且小、可逆 → 直接实现；新项目先完成下面的简短架构讨论。结果或约束不清楚 → 只问最少的一个具体问题，得到答案就继续。
- **好档**：把目标 / 偏好 / 约束 / 验收分开——目标缺失就先问“你拿这东西最终想达成什么”；“最好别用 X”“越小越好”先分清是硬约束还是偏好；“简单 / 好看 / 稳定”翻成几条看得见的标准。
- **需求严重纠缠**（多个独立目标、需求持续膨胀、方案与约束混作一层）：**直接起 `clarify-needs`**，起之前说一句为什么要多问这一轮。用户说“别问了直接做”就立刻收，退回只问最少的一个问题。省档微任务不起它。

### 新项目架构与好档方案

**新项目不分档，搭脚手架、写实现前先讨论适合它的架构，方向谈定后开始**；已明确架构或授权“你定 / 直接做”就推进，不重复索要点头。小脚本一句职责分工也可，不为架构名字建空层。Clean 分层是应用的重要候选，**选定后才启用其契约**，不统一强制；展示层不默认 MVVM，按 `vibe-apps` 的展示状态规则和框架自带绑定走。普通修改沿用既定方向，只有新目标、迁移要求或边界变化才重谈相关部分。

命中以上架构讨论，读 [references/planning.md](references/planning.md) 的架构部分；好档探方案读其方案部分，执行三点短设计与变化轴、适用的搭建图、原型、取舍翻译及定稿告知。界面效果图仍由 `vibe-apps` 管；方向已定后的细化图只告知，不重复审批。**尚未谈定且未获委托的架构方向，或此前未确认、会改变体验/数据/范围的选择，必须等用户决定**；其余已授权工作继续。

### 用户与 AI 的决策边界

用户决定：目标、可见行为、范围和优先级；新项目讨论后的架构方向（可以委托 AI 决定）；时间 / 成本取舍；删除、覆盖、迁移、联网、隐私等数据影响；会改变产品含义的取舍。

AI 决定并说明：已定架构内的库、模块细分、文件名、内部 API（模块和数据流属于架构层，按上面的条件画图给用户看）；普通实现细节和测试工具；不改变用户体验的可逆技术选择。

已定架构内的纯技术实现选择不许反问用户；拿不准就交给决策者（[references/collaboration.md](references/collaboration.md)），不是交给用户。要用户拍板的点，一律先翻译成后果再问——用户参与架构方向和结果取舍，不承担代码细节的决策。

**用户主动指定或讨论语言、框架时，直接回应并遵守已明确的选择。** 上面的默认决策边界与“不讲语言、库、框架”只约束 AI 不主动把内部选型抛给用户，不能覆盖用户已确认的技术约束。普通修改沿用已有项目的路线、语言和框架，不因分支默认而自动迁移。

### 谈定就记下来，动手前读回（不分档）

讨论里定下的东西从谈定到收工只活在对话里：一压缩就丢细节，丢的常是最早、最根本的那句；来回纠正时又容易只盯最新一句。所以谈定当场记，动手前读回。**只记不读等于没记。**

- **记什么**：用户第一次明确说出的核心目标和硬约束（一出现就记）；用户对具体做法点头，或纠正了你的理解；决策者审完你采纳或否决的结论（写“采纳 codex 建议：……”，没采纳的不写成约束）。没谈出结论的、纯技术又没经审的细节不记；已写进 `NEEDS.md` 当前需求区的不重复。
- **记在哪**：`HANDOFF.md` 的「已谈定」区，放最前，标签只能写 `**已谈定**：` 或 `## 已谈定`（压缩后读回的钩子只认这两种）。位置按 §6（项目 `docs/HANDOFF.md`，旁挂 `<脚本名>.HANDOFF.md`）；还没有就建一份只含这一区的。微脚本要跨会话接着聊也可以建旁挂的，不连带整套文档、不升档；做完由主 agent 把仍要守的约定并进头部契约行，再删掉它。
- **怎么记**：一事一条，单独能看懂，不写“按上面的方案”：`日期 · 来源 · 事项：当前结论；排除的做法及理由（如有）`，来源写“用户”或“采纳 codex 建议”。补充条件合进原条，不另起一条只留最新一句；明确推翻才改写，被推翻的做法删掉，仍有效的否决理由留在“排除”里。
- **谁记**：干活的主 agent 当场记，一条一两行；只动这一区，不为此加载 `living-blueprint`、不整理别的文档。只读或没有写权限时，在回复末尾列出待记的条目。
- **读回**：接手、恢复会话或压缩之后，先读「已谈定」区（和 `NEEDS.md` 当前需求区，有的话）。每次据此调整方案或开始实施之前，对照原始目标和全部仍有效的条件——本轮没再提到，不等于取消了。用户最新的明确指示可以更新旧约定（改写那一条）；当前有效约定优先于压缩摘要。
- **偏离信号**：用户指出之前说过的条件被漏了或理解错了（“我说了……”“我当时不是说……”“你理解错了”），或你发现当前方案和「已谈定」冲突——立即读回全部有效约定，按整体修正，不只改最新一句，并把漏掉的条件补进去。明确的纠正直接执行，不让用户把说清的再点一遍头；只有仍有歧义或约定互相冲突时，才问那一个具体问题。

## 5. 选择实现分支

| 场景 | 路由 |
|---|---|
| 独立 Python 命令行脚本、小工具、自动化 | 加载 `vibe-scripts` |
| 有界面的个人应用（Python、明确选择的 Rust 或其他已有实现） | 加载 `vibe-apps`，按实际需求选原生/Web 分支 |
| 公司固件、产品代码、构建系统或已有正式仓库 | 遵守该仓库规范；不要套个人工具技术栈 |
| 不属于以上类型 | 沿用项目现有结构，以最小改动完成 |

两个 vibe-* skill 内部各有自己的分级（微 / 标准 / 工具包），**按代码本身定级**，与档位无关。

### 低耦合底线与可插拔（所有档、所有脚本和应用）

低耦合是底线，不是好档的加分项；档位只决定做到多厚。公司固件 / 产品代码按该仓库规范，不套这一节。

- **逻辑与 IO / 界面分开**：算东西的函数不读写文件、不打印、不碰网络和设备，输入显式传进来、结果返回出去。微脚本做到“纯函数 ＋ `main()`”就够。
- **依赖单向**：外层（命令行、界面、适配器）调逻辑，逻辑不知道外层存在。不靠全局状态串模块，要用的东西作参数传进来。有界面应用按 `vibe-apps` 讨论并确定适合的架构；选定 Clean 分层时按其契约分离业务编排、展示与 IO，并按改动规模验证边界；CLI/微脚本没有 GUI，不套展示状态规则。
- **替换就删旧入口**：新实现接管旧功能时，同一次改动把调用方改到新位置并删掉旧函数 / 旧入口，不把旧入口改成转调新实现留着——那样旧模块会反过来依赖新模块、悄悄成环，没人调用也不报警。只有确有外部调用方的公开接口（插件 API、给别人用的库、CLI 参数）才留兼容层，并写明什么时候删。
- **外部数据和默认运行策略集中一处**：默认模型、端点 / URL、外部价格与配额这类值，标准级以上放配置文件、微脚本放头部具名常量区；入口读取校验后传参，逻辑不自己读配置、不另写默认值。必需配置出错就明确报错、停下受影响的操作，不许悄悄回退。哪些不算、能力与选择怎么分 → [references/low-coupling.md](references/low-coupling.md)。
- **变化轴**（以后会增、删、换的那类东西：平台、厂商、格式、数据源、输出目标、存储后端）：写代码前问一句“这里以后会不会再来一个同类的，或者去掉一个？”。**只有一个实际成员**：不为多实现扩展建注册表或通用接口，只要求它的代码聚在一处；选定 Clean 分层的应用跨 IO 边界所需的窄 ports 单独建立，不受此限制。**出现第二个实际成员，或调用方开始按成员名单 / 成员名分支**：先收口成“一份注册表 ＋ 每成员一个适配器”再加行为，收口算本次改动。验收：加或去掉一个成员，只动它自己的适配器和注册表。测试替身不算成员。什么算成员、适配器体量、唯一权威来源、故障隔离、存量已经散了怎么办 → [references/low-coupling.md](references/low-coupling.md)。
- **AI 宿主平台**（Claude Code、Codex……）按需适配：先只做正在用的平台，首次交付前把路留好，换平台时由那个平台的 AI 自己适配 → [references/platform-porting.md](references/platform-porting.md)。只是被 AI 编写或调用的普通脚本不算。

## 6. 留文档（按工具寿命，不按档位）

本节只管**哪些项目要哪些文件、放哪**，是这件事的唯一权威出处；每份文件写什么、什么时候更新，归 `living-blueprint`。

| 项目 | 要带的文件 |
|---|---|
| **微脚本**（定义以 `vibe-scripts` 定级表为准：<100 行、单一功能、IO 形式单一） | 只有脚本头部的契约行（结构 / 用途 / 用法 / 原始需求），不另建文档 |
| **和别的脚本共处一个目录的单文件脚本** | 同名旁挂 `<脚本名>.BLUEPRINT.md` ＋ `<脚本名>.CHANGELOG.md`；有没做完的活时再加 `<脚本名>.HANDOFF.md`。头部 `结构:` 行代替 AGENTS.md |
| **独占一个目录的项目**（不管是单文件脚本、工具包还是应用） | 项目根 `AGENTS.md` ＋ `docs/BLUEPRINT.md` ＋ `docs/CHANGELOG.md`；有没做完的活时再加 `docs/HANDOFF.md` |
| 好档、需求仍在演化 | 另加 `docs/NEEDS.md`（归 `clarify-needs`） |
| 公司固件 / 产品代码 | 按该仓库规范，不套本节 |

- 分界按**目录归属**，不按代码大小：独占目录就有 AGENTS.md，和别的脚本挤在一起就用旁挂文件。
- `HANDOFF.md` 只在有没做完的活时存在，做完删掉——没有这个文件就表示没有进行中的工作。讨论阶段谈定了东西、还没开工时，也可以先有一份只含「已谈定」区的（§4）。
- **同一件事的进度只记一处**：进度和交接只写 HANDOFF，不写进 pstate，也不写进平台原生记忆或 hub 金库（记忆只存长期结论和教训，看到进度类条目就以 git log 和 HANDOFF 为准，删掉或改成指针）。pstate（project-state 插件）管的是另外两件：**立项前的待续事项**（聊过什么、要不要做；决定做并落进 Obsidian 任务目录后转交，不再并行跟踪）和**会话互斥**（改某个 Obsidian 任务的文档或代码前先 `claim <任务目录>`，防同一件事被两个会话各做一遍；文件占用由钩子自动登记，撞上拦下）。它的旧待办看板已停用，不新建条目。公司仓不建 vibe 文档，也不加锁。`03-悬着的事` 只是发现入口：从它那里捡起一件事，进度落回 HANDOFF，不在它那里维护。
- 项目级只建 AGENTS.md，两个平台读同一份；只有当前环境的 Claude Code 确实不读 AGENTS.md 时，才加一个内容只有一行 `@AGENTS.md` 的 CLAUDE.md。

文档是连续工作的记忆，不是开工许可证。不要同时生成一套重复的需求、设计、计划文档。

## 7. 计划内执行交给监工，必要时叫外援

**已确定的多任务实施计划默认用批次监工**；小改直接做，不强拆三层。主会话只管计划、§4 用户决策和短简报，不并行实施、逐项复核或接回普通排错；监工负责整批派工、重试、集成、验证和文档。先实际核验宿主嵌套与结果路由；缺能力就明确降为已验证方式，不把记录工具当调度实现。

首次启动与交接按 [references/batch-supervisor.md](references/batch-supervisor.md) 的主会话部分；零上下文监工与执行角色按 [references/role-reading.md](references/role-reading.md) 加载。只有全部子任务已结束或确认停止才交接，不支持在途迁移；主会话用 `scripts/batch_state.py status` 看短状态，上行最多八行。

外援的触发、轻档/重档的复核密度与停止条件唯一见 [references/collaboration.md](references/collaboration.md)；有新实质取舍或需关键结果复核时按该文件调用 `ai-room`。角色、档位和评审结论由派工传递，已审方案不重复咨询。执行负责人复核产出；监工模式不退回主会话逐项复核。变更目标、范围或已确认行为才上报；危险的当前动作立即停止。

## 8. 实现与验证

实现时始终保持轻量：先交付最小但完整、可实际使用的一条行为链；保留已有行为、规则和用户写下的意图，不为简化或解决冲突而静默删除——遇到会改变行为的冲突，指出来等用户决定；不默认要求 TDD、正式计划、工作树或子代理，仅在好档中风险确实高、或用户明确要求时单独采用（已谈定多任务计划的监工按 §7；收工派 fork 也不在此列）；修改范围与授权一致，不顺手重构无关代码。

**所有档都必须做一次与交付形态相符的实际使用检查**——只跑单测、不跑用户真实入口不算。此外按档追加：

- **省档**：用代表性输入跑通即可，不为测试形式本身搭框架。
- **好档**：数据转换、持久化、迁移、已知回归、边界组合，增加针对性自动化测试；UI 要启动并走通核心用户路径；要可分发产物，就构建后运行该产物。
- **公司固件 / 产品代码**：遵守仓库规定的编译、静态检查、测试、真机或协议验证。无法执行的验证要明确说明，不能把“看起来正确”写成“已完成”。

**修 bug 先复现**（个人脚本和应用，所有档；只管修 bug，不是全面 TDD）：动手修之前先写一个能复现它的自动化测试，确认它在修之前失败；修完它通过，再跑一遍已有的全部测试，不只跑新加的那条。复现测试留在测试集里。没有测试集的微脚本，用一条能复现问题的命令做修前修后对比。依赖真机、时序或界面观感、实在无法自动复现的，写明手动复现步骤和修后实际看到的结果，不硬造一个复现不了问题的测试。

**结构也要验**（个人脚本和应用）：所有档交付前做**拔插自查**——本次动到的变化轴，调用方里有没有另写的成员名单或按成员名特判；动到外部数据 / 默认运行策略的再做**配置取值自查**；好档新建或收口了变化轴的补**结构测试**。后两项的做法见 [references/low-coupling.md](references/low-coupling.md) 第 3 节。

**依赖图前后对比**（好档里新增、拆分、合并模块或跨模块重构时）：开工前记下当前提交，交付前跑 `scripts/dep_graph.py <项目目录> --against <该提交>`（单 crate Rust、Python）。新出现的环（退出码 1）要么消掉，要么在完成报告里说明理由；新增边数和新环写进报告，要给用户看图时加 `--d2`。它只看内部模块之间的依赖方向和环，不替代已选架构的禁止导入测试；宏、动态导入和 re-export 转手看不到。

**文档跟着改才算完成**：实施中只按 §4 即时记录；监工另管批次机器区，不整理其他文档。实现者只负责应用脚手架的架构约束段、DESIGN/效果图；需求梳理归 `clarify-needs`。本批验证后、汇报前（微脚本免），或未完要结束会话时，按 [references/doc-fork.md](references/doc-fork.md) 派文档任务、等其结束并核对代码未动；无可用子任务才由执行负责人按 `living-blueprint` 自行处理。监工模式不把文档收尾退给主会话。

文档闸、压缩后读回、代码指纹与最终 HANDOFF 清理细则见 [references/doc-fork.md](references/doc-fork.md)。不触发闸不等于文档合格；不得为过闸写假条目或假回执。

**所有档（含微脚本）完成时简洁报告**：交付了什么；实际验证了什么（含拔插自查）；文档改了什么或不适用；哪些高风险项尚未验证。

## 9. 收工之后（只在命中时提一句，不是收尾仪式）

省档做完就结束，什么都不提。好档在命中下列情形时，**用一句话告诉用户有这个动作可用**，用户要才做：

| 命中情形 | 可用动作 |
|---|---|
| 迭代多轮、开始觉得“这块是不是不用做” | `cut-scope` 剪枝（只读，只给方向） |
| 做到能用了，想知道生态位和能抄的点 | `scan-field` 的**回头那头**（产原创度对比 + 升级方向文档） |
| 这轮做的正好是 skill / 插件本身 | `skill-review` 复盘（在 xu-skills 插件） |
