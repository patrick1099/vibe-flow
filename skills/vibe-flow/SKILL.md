# Vibe Flow：轻量 vibe-coding 主流程

## 核心原则

> 先明确需求，再判这是小事还是大事：**小事要省，大事要好。**

省的是流程，不是质量；好的是该厚的地方厚，不是每次走满。本 skill 是这套工作流的**总入口与档位闸门**，只做判档、路由和决策边界，不复制各 skill 的正文，也不把它们串成必经关卡。

## 整套工作流总图

一次判档，全流程沿用同一档。**不命中的环节完全不提**——这张图是路由图，不是阶段清单。

| 环节 | 省档（默认） | 好档 | 用什么 |
|---|---|---|---|
| 判意图 | 都要 | 都要 | §1 |
| 判档 | 都要（一次） | 都要（一次） | §2 |
| 开工前 | 查自己有没有现成的 | ＋查市面有没有 | §3、`script-manager` / `scan-field` |
| 明确需求 | 不澄清，或只问一个问题 | 挖目标 / 分清偏好与约束 / 翻译验收 | §4、`clarify-needs` |
| 探方案 | 不探，直接做 | 多条路给 2–3 个方案 + 取舍；界面类出原型让你挑 | §4 |
| 实现 | 最小可用，禁套架构 | 按分支的完整纪律 | §5、`vibe-scripts` / `vibe-apps` |
| 留文档 | 不建 | `NEEDS.md`；长期项目上 `BLUEPRINT.md` | §6、`living-blueprint` |
| 外援 | 不咨询；机械活照样甩给 opencode | 实质取舍咨询决策者(claude↔codex)，机械活甩给 opencode | §7、`ai-room` |
| 验证 | 代表性输入跑通 | 按交付形态实际使用 ＋ 针对性测试 | §8 |
| 收工后 | 无 | 膨胀了剪枝 / 完工了扫同款 / 更新蓝图 | §9、`cut-scope` / `scan-field` |

## 1. 先判断用户此刻要什么

| 请求 | 动作 |
|---|---|
| 可行性、解释、比较、只读诊断 | 先直接回答；不要擅自转成建项目或改文件 |
| 明确要求构建、修改或修复 | 进入后续流程并完成实现与验证 |
| “可以 / 继续 / 按这个做”且方案已经谈定 | 视为继续实现，不再重复索要批准 |

回答“能不能实现”时，先给结论和关键限制。只有用户要求继续做，或上下文已经明确授权改动，才进入实现。

## 2. 判档（承重环节，判一次）

**默认省档。升到好档必须说得出具体理由，并在回复里说一句。** 不对称是故意的：省是默认，厚要理由。

**升档判据**——命中任一即好档：

- **会再用**：不是跑完即弃，以后还会拿出来用或改。
- **不可逆**：删除、覆盖、迁移数据，联网上传，或发出去收不回。
- **给别人**：要分发（exe / 仓库 / 插件），或别人会依赖它。
- **跨会话**：一次做不完，下次会话还得接着做。
- **多目标纠缠**：两个以上独立目标或独立用户。

这五条**故意都是不必深挖需求就能知道的外部事实**，所以判档不必等澄清做完——先粗判，按档澄清，澄清中发现事实变了就升档（只升不降，并说明原因）。

**用户一句话直接定档，优先于以上判据。** 听到“这个随便做一下 / 按小事做”→ 省档；“这个要做好 / 以后长期用”→ 好档。此时不要再自行推翻，也不要反问判据。

## 3. 开工前：先看有没有现成的

分两问，从近到远。

**① 自己有没有（两档都做，很便宜）**：要写独立脚本或小工具前，先查 `script-manager` 的 `INDEX.md`（本机个人脚本登记册，装了才有），能复用就别重造；已有脚本改一点就够用时，改它而不是新建。

**② 市面有没有**：查完仍要新建或重写，且要做的东西**能拿出去**（插件 / 工具包 / 产品 / 会长期活的工具），或**打算重写替换一个已有的东西** → 交给 `scan-field` 的**开口那头**（薄：几分钟、几句话、不落文档，结论只有「有现成的直接用 / 有邻近款先抄点子 / 没搜到放心做」三种）。日常改功能、加子命令、修 bug、一次性微脚本**不扫，一个字都不提**——缩放闸由 scan-field 自己判，本节只负责把请求交过去。

> 真正的浪费只有一种：不知道同款存在。规则不是禁止造轮子，是动手前先看过。

## 4. 明确需求，必要时再探方案

先检查三件事：

1. 用户真正想得到的可见结果是什么？
2. 用户说的是目标、偏好、建议方案，还是不可违反的硬约束？
3. 哪些缺失信息会让最终行为、数据、成本或范围明显不同？

**只澄清会改变结果的内容**，按档决定厚度：

- **省档**：清楚且小、可逆 → 直接实现，不澄清。结果或约束不清楚 → 只问最少的一个具体问题，得到答案就继续。
- **好档**：把目标 / 偏好 / 约束 / 验收分开——目标缺失就先问“你拿这东西最终想达成什么”；遇到“最好别用 X”“越小越好”先分清是硬约束还是偏好；遇到“简单 / 好看 / 稳定”翻成几条看得见的标准。
- **需求严重纠缠**（多个独立目标、需求持续膨胀、方案与约束混作一层）：`clarify-needs` 标了 `disable-model-invocation`，**你无法自己启动它**——请用户手动调 `/vibe-flow:clarify-needs`，并说明这一步能帮他把目标和方案分开。用户不想调就别卡住，按上面好档的问法自己问。

### 探方案（只在好档且真有多条路时）

- **只有一条明显路**：不探，直接做。
- **涉及数据模型、持久化、主要 UI 流程、模块边界或分发方式**：用三点短设计说明“怎么做 / 为什么 / v1 明确不做什么”，然后继续。
- **确实有 2–3 条各有取舍的路**：并排给出方案、各自代价、你的推荐，让用户拍。别只报一个方案当既定事实，也别把选项堆到五个。
- **涉及界面、观感、交互**（"看到才知道自己要什么"那类）：**别追问"你想要什么风格"——用户答不出来。** 改成给 2–3 个小原型 / 草样让他挑；他说不清时请他扔**参照物**（截图、链接、他觉得好的现成产品），拿参照物代替形容词。这是**用示例替代提问**，比问更省，属于探方案而不是澄清需求。
- 想要完整的 brainstorming → 计划落盘 → 按计划执行（带 dated spec/plan），手动调 `superpowers-manual` 那套。**本流程不依赖它，没装也能走完全程。**

### 用户与 AI 的决策边界

用户决定：

- 目标、可见行为、范围和优先级
- 时间/成本取舍
- 删除、覆盖、迁移、联网、隐私等数据影响
- 会改变产品含义的取舍

AI 决定并说明：

- 库、模块划分、文件名、内部 API
- 普通实现细节和测试工具
- 不改变用户体验的可逆技术选择

纯技术内部选择不许反问用户。

## 5. 选择实现分支

| 场景 | 路由 |
|---|---|
| 独立 Python 命令行脚本、小工具、自动化 | 加载 `vibe-scripts` |
| 有界面、要打包分发、可能成长为网站的个人 Python 应用 | 加载 `vibe-apps` |
| 公司固件、产品代码、构建系统或已有正式仓库 | 遵守该仓库规范；不要套个人工具技术栈 |
| 不属于以上类型 | 沿用项目现有结构，以最小改动完成 |

澄清方式可以共用；实现结构与验证强度由分支 ＋ 档位共同决定。两个 vibe-* skill 内部还各有自己的分级（微 / 标准 / 工具包等），省档通常落在其最低一级。

## 6. 留文档（按档，不按仪式）

- **省档**：不建需求文档。
- **好档、需求仍在演化**：维护简短 `docs/NEEDS.md`，记录当前目标、可见行为、硬约束和暂不做。
- **好档、长期维护且以后会按意图重构**：用 `living-blueprint` 建并维护 `docs/BLUEPRINT.md`（只讲功能不讲实现的当前全貌）。

文档是连续工作的记忆，不是开工许可证。不要同时生成一套重复的需求、设计、计划文档。

## 7. 必要时才用 ai-room 叫外援

`ai-room` 里角色是固定的：**claude 和 codex 是咨询者兼决策者，opencode 只当执行者。** 你是 claude 就问 codex，是 codex 就问 claude。据此有两种用法。

**用法一 · 咨询决策者。** 只有同时满足以下两条才叫：

- 需求已经清楚；
- 仍有一个会实质影响架构、可维护性或迁移成本的技术取舍。

**没有第三条前置条件。** `ai-room ask` 是无头的：一条命令派一个一次性子 agent，不需要用户开第二个窗口，跑完即返回。所以**决定要外援就直接派，不要反问用户"要不要开一个 codex 窗口"**——那是把一件一条命令能办的事变成一次协商。只有用户自己点名要"两个窗口互当顾问 / 走信箱"，才改用那个对话模式。

```bash
ai-room ask --to codex --cwd <项目根> --related-doc <精确路径> \
  --question "项目是<X>，要解决<Y>。约束：<Z>。我的方案是<方案>，不确定的是<疑点>。请判断是否成立、哪里必须改。"
```

交的是**你自己的方案**，让他挑毛病，不是让他替你想。保持默认 `read-only`——决策者不动手。一次一个具体问题，把它需要的每条精确路径给全，绝不"帮我全面 review 一下"。

**用法二 · 派 opencode 执行。opencode 是廉价劳力，随便用。** 凡是判断成分低的机械活，默认就该甩过去，别自己埋头做：批量改名/替换、跑格式化、加日志、照现成模式补样板代码、跑测试构建并把失败摘出来、写死板的单测骨架、大范围 grep 汇总、改错别字补注释补类型标注。

```bash
ai-room ask --to opencode --permission workspace-write --cwd <项目根> --related-doc <精确路径>   --question "项目是<X>。这一件任务：<一件事>。完成标准：<可验证标准>。不要动<边界外>。"
```

**派 opencode 本身没有门槛，有门槛的是咨询。** 判定只有一句：

> **这件事有没有技术取舍？** 没有 → 直接派 opencode，不用问任何人。有 → 先咨询决策者把方案定下来，再拆成任务派。

机械活不需要咨询，因为**根本没有方案可审**。「先咨询、后执行」约束的是**方案**，不是每一次派发：opencode 不许执行没人审过的**方案**，但一个方案审过之后，从它拆出来的多件任务不必每件重审。

**咨询审多少由档位决定**，这是本 skill 的职责；`ai-room` 只保证"有方案的活，方案至少被审过一次"：

| 情形 | 咨询密度 | 能不能派 opencode |
|---|---|---|
| **机械活**（无技术取舍） | **不咨询** | 随便派，鼓励派 |
| **省档** | 不叫外援 | 实现里的机械部分照样派 |
| **好档 · 轻**（升档理由是「会再用」「跨会话」「多目标纠缠」） | **只审方案**：开工前咨询一次，之后照方案走，冒出**新的**实质取舍才再咨询 | 方案定稿后拆任务派 |
| **好档 · 重**（升档理由命中「不可逆」或「给别人」） | **方案审 ＋ 每步结果审**：每步派完把结果送回决策者过一眼，通过了再派下一步 | 同上，逐步派 |

「重」不是第三个档位，是好档内部按已有的升档判据再分——理由是不可逆或要给别人的，本来就该比"以后还会再用"厚。判档仍然只判一次。

逐步回审必须有停止条件，否则会长成本节明令禁止的无限评审循环：**同一个问题不得二次送审；决策者说通过就往下走，不要求他背书两遍；连续两步没有新问题就停止回审，剩下的自己复核。**

无论哪一档，opencode 的产出**你自己复核**——它是执行者不是负责人。

两种用法都必须把**场景上下文**说全：子 agent 是零上下文的，它不知道你在做什么项目、前面聊过什么。读回来的一行 JSON 看 `ok` 和 `text`：采纳或说明取舍后继续，**不要无新问题反复送审**。它说需要用户拍板时，仅当那个阻塞真的跨越用户决策边界才去问用户，否则自行决断。

要省的是**咨询**，不是派发：别为简单问题、每个功能后的例行审查、"审查所有东西"或无限评审循环去占用决策者。派 opencode 干机械活恰恰相反——那是在省你自己的时间，多派。命令细节、超时坑和压缩规则由 `ai-room` skill 自己负责，本 skill 不复制。

## 8. 实现与验证

实现时始终保持轻量：

- 先交付最小但完整、可实际使用的一条行为链。
- 保留已有行为、规则和用户写下的意图；不能为了简化或解决冲突而静默删除。
- 不默认要求 TDD、正式计划、工作树或子代理；仅在好档中风险确实高、或用户明确要求时单独采用。
- 遇到会改变行为的冲突时，指出具体冲突并等待用户决定；不要替用户删需求。
- 修改范围与用户授权保持一致，不顺手重构无关代码。

**所有档都必须做一次与交付形态相符的实际使用检查**——这是省档也不能省的底线。此外按档追加：

- **省档**：用代表性输入跑通即可，不为测试形式本身搭框架。
- **好档**：数据转换、持久化、迁移、已知回归、边界组合，增加针对性自动化测试；UI 要启动并走通核心用户路径（只检查语法或接口响应不算）；用户要可分发产物，就构建后运行该产物，而不只验证源码模式。
- **公司固件 / 产品代码**：遵守仓库规定的编译、静态检查、单元/集成测试、真机或协议验证及文档一致性检查。无法执行的验证要明确说明，不能把“看起来正确”写成“已完成”。

完成时简洁报告：

1. 交付了什么；
2. 实际验证了什么；
3. 哪些高风险项尚未验证。

## 9. 收工之后（只在命中时提一句，不是收尾仪式）

省档做完就结束，什么都不提。好档在命中下列情形时，**用一句话告诉用户有这个动作可用**，用户要才做：

| 命中情形 | 可用动作 |
|---|---|
| 迭代多轮、开始觉得“这块是不是不用做” | `cut-scope` 剪枝（只读，只给方向） |
| 做到能用了，想知道生态位和能抄的点 | `scan-field` 的**回头那头**（产原创度对比 + 升级方向文档） |
| 这轮改变了工具的可观察行为，且项目有 `BLUEPRINT.md` | 更新蓝图（`living-blueprint`） |
| 这轮做的正好是 skill / 插件本身 | `skill-review` 复盘（在 xu-skills 插件） |

## 反模式

- 用户问可行性，却先输出一整套流程或开始改文件
- **把上面那张总图当必经阶段依次跑**——它是路由图，不命中的环节一个字都不该出现
- **不判档，或每个环节各判一次导致前后档位不一致**（澄清按小事、验证按大事，或反过来）
- 判成好档却说不出命中哪条判据；或用户已明说“随便做一下”还硬升档
- 清楚的小需求仍连续追问、写长方案、反复请求批准
- 把纯技术内部选择甩给用户
- 所有项目强制 brainstorming、TDD、BLUEPRINT 或多代理
- 为“简化”静默删掉原有 rules、行为或需求
- 只跑单测，不跑用户真实入口
- 把第二个 AI 变成永不结束的审查门
- 声称自己能启动 `clarify-needs`（它禁用了模型调用，只能请用户手动调）
