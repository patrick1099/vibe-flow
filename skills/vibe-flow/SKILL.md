# Vibe Flow：轻量 vibe-coding 主流程

## 核心原则

> 先明确需求，再判这是小事还是大事：**小事要省，大事要好。**

省的是流程，不是质量；好的是该厚的地方厚，不是每次走满。本 skill 是这套工作流的**总入口与档位闸门**：`vibe-scripts` / `vibe-apps` / `clarify-needs` 都先经过这里判档再进。跨分支的规矩（低耦合 §5、文档 §6、谁拍板 §4）以本 skill 为唯一权威出处，分支 skill 只给代码例子；不把各 skill 串成必经关卡。

## 整套工作流总图

一次判档，全流程沿用同一档。**不命中的环节完全不提**——这张图是路由图，不是阶段清单。

| 环节 | 省档（默认） | 好档 | 用什么 |
|---|---|---|---|
| 判意图 | 都要 | 都要 | §1 |
| 判档 | 都要（一次） | 都要（一次） | §2 |
| 开工前 | 查自己有没有现成的 | ＋查市面有没有 | §3、`script-manager` / `scan-field` |
| 明确需求 | 不澄清，或只问一个问题 | 挖目标 / 分清偏好与约束 / 翻译验收；有流程的画「它跑起来是什么样」图 | §4、`clarify-needs` |
| 探方案 | 不探，直接做 | 技术取舍 AI 定、决策者审；影响用户的翻译成后果再问；界面类出原型让你挑；多模块的画「我打算怎么搭」图；定稿后白话告知方向即开工 | §4 |
| 实现 | 最小可用；守低耦合底线，不预建插口 | 按分支的完整纪律；变化轴列进三点设计 | §5、`vibe-scripts` / `vibe-apps` |
| 留文档 | 按工具寿命，不按档：微脚本头部契约行；其余 `BLUEPRINT.md` ＋ `CHANGELOG.md`；有目录的＋`AGENTS.md`；有没做完的活＋`HANDOFF.md` | 同左；需求仍演化时＋`NEEDS.md` | §6、`living-blueprint` |
| 外援 | 不咨询；机械活照样甩给 opencode | 实质取舍咨询决策者(claude↔codex)，机械活甩给 opencode | §7、`ai-room` |
| 验证 | 代表性输入跑通 ＋ 拔插自查；给别人的按交付形态跑 | 按交付形态实际使用 ＋ 针对性测试 ＋ 结构测试 | §8 |
| 收工后 | 无 | 膨胀了剪枝 / 完工了扫同款 | §9、`cut-scope` / `scan-field` |

## 1. 先判断用户此刻要什么

| 请求 | 动作 |
|---|---|
| 可行性、解释、比较、只读诊断 | 先直接回答；不要擅自转成建项目或改文件 |
| 明确要求构建、修改或修复 | 进入后续流程并完成实现与验证 |
| “可以 / 继续 / 按这个做”且方案已经谈定 | 视为继续实现，不再重复索要批准 |

回答“能不能实现”时，先给结论和关键限制。只有用户要求继续做，或上下文已经明确授权改动，才进入实现。

## 2. 判档（承重环节，判一次）

判两件互不相干的事，别混：

| 维度 | 看什么 | 决定什么 |
|---|---|---|
| **档位**（流程厚度） | **本次改动**本身 | 澄清几轮、探不探方案、叫不叫决策者、验证多厚 |
| **产物要求** | **工具寿命和去向** | 要不要文档（§6）、要不要按交付形态验证（§8） |

**一个长期工具上的明确小改，档位是省档**——项目活多久不让这次改动变厚；它只决定文档要跟着改。

### 档位：默认省档，升档要理由

**升到好档必须说得出命中哪条，并在回复里说一句。** 升档判据只看本次改动，命中任一即好档：

- **范围或影响面大**：新加一整块功能、牵连很多文件、要新建的工具本身就复杂（多个模块、多种输入输出）；或改动虽小但影响面广——单位换算、统计口径、共享数据的写入，一错就影响全部数据。**“新建”本身不升档**：需求清楚的小脚本，新写也是省档。
- **出错后果重 / 不可逆**：删除、覆盖、迁移数据，联网上传，发出去收不回；或错了会污染已有数据、很难发现。
- **关键未知**：有会实质改变行为、数据或方案的未知。普通实现细节拿不准不算，那是 AI 自己查、自己定的。
- **多目标纠缠**：两个以上独立目标或独立用户搅在一起。

这几条**都能在不深挖需求的情况下粗判**——先粗判，按档澄清，澄清中发现事实变了就升档（只升不降，并说明原因）。**「以后还会用」「要给别人」「一次做不完」都不是升档理由**：前两个归产物要求，最后一个由 `HANDOFF.md` 承接（§6）。

**用户一句话直接定档，优先于以上判据。** 听到“这个随便做一下 / 按小事做”→ 省档；“这个要做好 / 好好想想”→ 好档。此时不要再自行推翻，也不要反问判据。

### 产物要求：看工具寿命和去向

- **会再用**（不是跑完即弃）→ 文档按 §6（微脚本仍然只用头部契约行）。
- **给别人**（分发 exe / 仓库 / 插件，或别人会依赖它）→ 验证按交付形态做（§8：构建后实际运行该产物）。
- 两者都不改变档位。

## 3. 开工前：先看有没有现成的

分两问，从近到远。

**① 自己有没有（两档都做，很便宜）**：要写独立脚本或小工具前，先查 `script-manager` 的 `INDEX.md`（本机个人脚本登记册，装了才有），能复用就别重造；已有脚本改一点就够用时，改它而不是新建。

**② 市面有没有**：查完仍要新建或重写，且要做的东西**能拿出去**（插件 / 工具包 / 产品 / 会长期活的工具），或**打算重写替换一个已有的东西** → 交给 `scan-field` 的**开口那头**（薄：几分钟、几句话、不落文档，结论只有「有现成的直接用 / 有邻近款先抄点子 / 没搜到放心做」三种）。日常改功能、加子命令、修 bug、一次性微脚本**不扫，一个字都不提**——缩放闸由 scan-field 自己判，本节只负责把请求交过去。

> 真正的浪费只有一种：不知道同款存在。规则不是禁止造轮子，是动手前先看过。

## 4. 明确需求，必要时再探方案

先检查三件事：

1. 用户真正想得到的可见结果是什么？
2. 用户说的是目标、偏好、建议方案，还是不可违反的硬约束？
3. 哪些缺失信息会让最终行为、数据、成本或范围明显不同？

**只澄清会改变结果的内容**，按档决定厚度：

- **省档**：清楚且小、可逆 → 直接实现，不澄清。结果或约束不清楚 → 只问最少的一个具体问题，得到答案就继续。
- **好档**：把目标 / 偏好 / 约束 / 验收分开——目标缺失就先问“你拿这东西最终想达成什么”；遇到“最好别用 X”“越小越好”先分清是硬约束还是偏好；遇到“简单 / 好看 / 稳定”翻成几条看得见的标准。
- **需求严重纠缠**（多个独立目标、需求持续膨胀、方案与约束混作一层）：**直接起 `clarify-needs`**，别自己硬问——它能自触发，不必等用户开口，但起之前说一句为什么要多问这一轮。用户说"别问了直接做"就立刻收，退回上面好档的问法问最少的一个问题。省档且是微任务时不要起它。

### 探方案（只在好档）

- **只有一条明显路**：不比方案，直接做。但满足下面「我打算怎么搭」图的条件时，图和三行白话照给——一条路只免方案比较，不免图。
- **涉及数据模型、持久化、主要 UI 流程、模块边界或分发方式**：用三点短设计说明“怎么做 / 为什么 / v1 明确不做什么”，**再加一行“变化轴”**：以后会增、删、换的是哪几类东西，各自现在有几个成员（认轴规则见 §5「低耦合底线」）。没有轴就写“无”，不许省掉这一行。然后继续。
- **「我打算怎么搭」图（与有没有多条路无关）**：好档，且**本次动到**至少两个职责模块，或数据要跨好几个处理 / 存储环节时，默认画——按这次实际动到的结构算，不数整个仓库有几个模块，也不按文件数算。画模块怎么分、各管什么、数据从哪到哪、存在哪，配一两句为什么这么分，随下面的三行白话一起给用户。用户懂架构这一层（模块、数据流、流程图），不懂具体语言和代码——架构藏起来他就没法及时插话。
  - **图是告知不是审批**：给完直接开工。内部架构拿不准的点由 AI 自己处理，该咨询决策者就按 §7 咨询，不上图问用户；只有此前没确认过、会改变使用体验或数据的点才标 `guess` 并问（照下面“会”那一支翻译成后果）。没有这类点，图上就没有待定项。
  - **用户看图后开口**：明确要改的照改；提问的先解释为什么这么搭；给建议的先判断采不采纳、说明理由，别把一句“为什么不这样”当成改动命令。
  - 库、语言、文件怎么写不上图、不问用户。用 `clarify-needs` 的 `scripts/model_page.py --layer build` 出（规矩见 `clarify-needs/references/run-model.md`）。给用户挑错的「它跑起来是什么样」运行图不受影响，照常由 `clarify-needs` 负责。
- **确实有 2–3 条各有取舍的路**：先按一句话分流——**选 A 和选 B，用户用起来会不会不一样？**
  - **不会**（只影响库、代码怎么分、内部数据结构这类技术内部）：AI 自己定，不问用户。好档按 §7 的密度交给决策者（codex）审方案，审完自己拍板。
  - **会**（快慢、要不要联网 / 能不能离线、会不会删改用户数据、多花多少时间、以后能不能加同类的东西）：把每条路**翻译成用户能感知的后果**再问，附你的推荐和理由。不讲语言、库、框架这一层的名词——不问“SQLite 还是 JSON”，问“数据多了以后，你要不要能按条件搜？”；模块、接口、注册表、适配器、分层、缓存这类架构词可以直接用，第一次出现时带一句解释。别只报一个方案当既定事实，也别把选项堆到五个。
  - 两种混在一起时，先让决策者把纯技术那部分定掉，只把剩下影响用户的点翻译了问。
- **涉及界面、观感、交互**（"看到才知道自己要什么"那类）：**别追问"你想要什么风格"——用户答不出来。** 改成给 2–3 个小原型 / 草样让他挑；他说不清时请他扔**参照物**（截图、链接、他觉得好的现成产品），拿参照物代替形容词。这是**用示例替代提问**，比问更省，属于探方案而不是澄清需求。
- **方案定稿后，用三行白话告知方向，然后直接开工，不等回复**（只在本节做过三点设计、多方案取舍，或画了「我打算怎么搭」图时；其余“只有一条明显路”的不用）：**我要做什么 / 做完你会看到什么、怎么用 / 这次明确不做什么**（画了图的附上图）。三行本身不含代码层细节，判据同 `clarify-needs`：能不能念给不懂代码的人听；架构词照上面的规矩，首次带解释。这是告知不是审批——方向在需求阶段已经一起定过，这三行只让用户能及时叫停；用户叫停就停下改方向。
- **什么时候必须停下来等用户**：只有出现**此前没确认过**、会改变使用体验、数据影响或范围的选择时（照上面“会”那一支翻译成后果再问）。已经确认过的方向（包括在运行图、原型里点过头的）不再重复要点头。
- 想要完整的 brainstorming → 计划落盘 → 按计划执行（带 dated spec/plan），手动调 `superpowers-manual` 那套。**本流程不依赖它，没装也能走完全程。**

### 用户与 AI 的决策边界

用户决定：

- 目标、可见行为、范围和优先级
- 时间/成本取舍
- 删除、覆盖、迁移、联网、隐私等数据影响
- 会改变产品含义的取舍

AI 决定并说明：

- 库、模块划分、文件名、内部 API（模块划分和数据怎么流属于架构层，按上面的条件画图给用户看，用户开口照上面的分法处理）
- 普通实现细节和测试工具
- 不改变用户体验的可逆技术选择

纯技术内部选择不许反问用户；拿不准就交给决策者（§7），不是交给用户。要用户拍板的点，一律先翻译成后果再问——用户决定的是“要什么”，不是“怎么做”。

## 5. 选择实现分支

| 场景 | 路由 |
|---|---|
| 独立 Python 命令行脚本、小工具、自动化 | 加载 `vibe-scripts` |
| 有界面、要打包分发、可能成长为网站的个人 Python 应用 | 加载 `vibe-apps` |
| 公司固件、产品代码、构建系统或已有正式仓库 | 遵守该仓库规范；不要套个人工具技术栈 |
| 不属于以上类型 | 沿用项目现有结构，以最小改动完成 |

澄清方式可以共用；验证强度由档位定。两个 vibe-* skill 内部各有自己的分级（微 / 标准 / 工具包），**按代码本身定级**（行数、子命令、变体），与档位无关：省档的小改动可以落在工具包级项目里，好档的新工具也可以只是标准级。

### 低耦合底线与可插拔（所有档、所有脚本和应用）

低耦合不是好档的加分项，是底线；档位只决定做到多厚，不决定做不做。公司固件 / 产品代码按该仓库规范，不套这一节。

**底线（含微脚本）**：

- 逻辑与 IO / 界面分开：算东西的函数不读写文件、不打印、不碰网络和设备，输入显式传进来，结果返回出去。微脚本做到“纯函数 ＋ `main()`”就够。
- 依赖单向：外层（命令行、界面、适配器）调逻辑，逻辑不知道外层存在。
- 不靠全局状态串模块：要用的东西作参数传进来。

**变化轴——以后会增、删、换的那一类东西**（平台、厂商、格式、数据源、输出目标、存储后端……）：

- **认轴**：写代码前问一句“这里以后会不会再来一个同类的，或者去掉一个？”会，就记成一条轴（好档写进 §4 三点设计的“变化轴”那行；省档心里过一遍）。**认轴只是记下来，动作按下面的实际成员数触发**，不按想象中的未来预建任何东西。
- **只有一个实际成员**：不建注册表、不建目录、不抽接口（YAGNI），只要求这个成员的代码聚在一处，不散进别处——给第二个成员留好搬家路。
- **什么算成员**：工具正式提供的可选运行方式才算——比如用户能选“真实设备 / 仿真设备”，仿真就是第二个成员。只在测试里临时传进去的假函数、假对象是**测试替身**，不算成员，不进运行时注册表；“要测试”本身不是建接口和注册表的理由（逻辑与 IO 分开后，测试直接喂数据就行）。
- **出现第二个实际成员，或调用方第一次出现成员名单 / 按成员名分支**：必须先收口成“一份注册表 ＋ 每成员一个适配器”，再加行为。这次收口是本次改动的一部分，不算顺手重构；不许在没收口的状态下复制第二份分支。
- **适配器按体量缩放**：标准级单文件脚本里，注册表是一张 dict，适配器可以只是一个函数或一条数据记录；只有工具包级才要求每成员一个文件。
- **唯一权威来源**：运行时的成员清单和成员特有的能力只有注册表这一处；调用方（CLI 选项、循环、校验、界面）一律从注册表派生，不另写名单，不按成员名分支（`if 成员 in (a, b)`、`成员 == a`）。按能力分支就让适配器自己声明能力，调用方去问适配器。测试、文档、示例配置、兼容迁移、用户可见的输出里出现成员名是正常的，不算违规。
- **收好之后的验收句**：加或去掉一个成员，只动它自己的适配器和注册表。做了下一条故障隔离的，再加半句“一个成员出错只影响它自己”。有 `BLUEPRINT.md` 的，把这句写进第 4 节硬约束。
- **故障隔离（只在成员各有外部依赖时要求）**：成员各自依赖第三方库、设备、网络、外部配置或文件时，一个坏了（依赖没装、配置缺失、导入失败），聚合类命令（状态检查、批量注册、全部同步）把它记成“不可用 ＋ 原因”，继续处理其余成员，最后按汇总结果定退出码；注册表只登记名字、惰性加载成员，不许因为一个成员加载失败而整体起不来。用户点名要这个坏成员，或操作本身要求全有全无时，明确失败并返回非零，不许静默部分成功。成员只是几个纯函数（比如两种格式转换）时，一张 dict 就够，不需要这套。
- **存量代码已经散了**（名单写死在多处）：本次改动正要增删这条轴的成员或改它的能力时，收口算本次功能的相关改动，照上面“第二个成员”那条办；收口范围明显超出本次改动（牵连很多文件）时先停下，说清散在几处，让用户选先收口还是先打补丁。本次没碰的其他轴只报告，不动。

具体到代码长什么样，由 `vibe-scripts` / `vibe-apps` 各自给模板；本节只定规矩，不绑语言。

## 6. 留文档（按工具寿命，不按档位）

本节只管**哪些项目要哪些文件、放哪**，是这件事的唯一权威出处；每份文件写什么、什么时候更新，归 `living-blueprint`。

| 项目 | 要带的文件 |
|---|---|
| **微脚本**（定义以 `vibe-scripts` 定级表为准：<100 行、单一功能、IO 形式单一） | 只有脚本头部的契约行（结构 / 用途 / 用法 / 原始需求），不另建文档 |
| **和别的脚本共处一个目录的单文件脚本** | 同名旁挂 `<脚本名>.BLUEPRINT.md` ＋ `<脚本名>.CHANGELOG.md`；有没做完的活时再加 `<脚本名>.HANDOFF.md`。头部 `结构:` 行代替 AGENTS.md |
| **独占一个目录的项目**（不管是单文件脚本、工具包还是应用） | 项目根 `AGENTS.md` ＋ `docs/BLUEPRINT.md` ＋ `docs/CHANGELOG.md`；有没做完的活时再加 `docs/HANDOFF.md` |
| 好档、需求仍在演化 | 另加 `docs/NEEDS.md`（归 `clarify-needs`） |
| 公司固件 / 产品代码 | 按该仓库规范，不套本节 |

- 分界按**目录归属**，不按代码大小：独占目录就有 AGENTS.md，和别的脚本挤在一起就用旁挂文件。
- `HANDOFF.md` 只在有没做完的活时存在，做完删掉——没有这个文件就表示没有进行中的工作。
- 项目级只建 AGENTS.md，两个平台读同一份；只有当前环境的 Claude Code 确实不读 AGENTS.md 时，才加一个内容只有一行 `@AGENTS.md` 的 CLAUDE.md。

文档是连续工作的记忆，不是开工许可证。不要同时生成一套重复的需求、设计、计划文档。

## 7. 必要时才用 ai-room 叫外援

角色固定：**claude 和 codex 是决策者（你是 claude 就问 codex，反之亦然），opencode 只当执行者。** 怎么调用、上下文怎么给、超时怎么续，全归 `ai-room` skill，本节只管**什么时候叫、审多少**。

- **咨询决策者**：需求已经清楚、且仍有一个会实质影响架构、可维护性或迁移成本的技术取舍，才叫。交的是**你自己的方案**让它挑毛病，一次一个具体问题。决定要叫就直接派，不反问用户“要不要开个窗口”。
- **派执行者**：没有技术取舍的机械活（批量替换、格式化、补样板、跑测试摘失败……）直接派，没有门槛。有取舍的，先让决策者把方案定下来再拆成任务派；方案审过一次，拆出来的任务不必每件重审。
- 决策者说“需要用户拍板”时，只有真跨过 §4 用户决策边界才去问用户，否则自己定。

**审多少由档位决定**：

| 情形 | 咨询密度 | 能不能派 opencode |
|---|---|---|
| **机械活**（无技术取舍） | **不咨询** | 随便派，鼓励派 |
| **省档** | 不叫外援 | 实现里的机械部分照样派 |
| **好档 · 轻**（升档理由是「范围或影响面大」「关键未知」「多目标纠缠」） | **只审方案**：开工前咨询一次，之后照方案走，冒出**新的**实质取舍才再咨询 | 方案定稿后拆任务派 |
| **好档 · 重**（升档理由命中「出错后果重 / 不可逆」，或要给别人且本次改动范围大） | **方案审 ＋ 关键步骤结果审**：关键步骤做完把结果送回决策者过一眼，通过了再往下；格式化、补样板这类机械步骤不逐个审 | 同上，逐步派 |

「重」不是第三个档位，是好档内部按已有的升档判据再分——错了代价大的，本来就该比"范围大"厚。判档仍然只判一次。

**停止条件**（防止变成无限评审）：同一个问题不二次送审；决策者说通过就往下走；连续两步没有新问题就停止回审，剩下的自己复核。执行者的产出一律自己复核——它是执行者不是负责人。要省的是咨询，不是派发。

## 8. 实现与验证

实现时始终保持轻量：

- 先交付最小但完整、可实际使用的一条行为链。
- 保留已有行为、规则和用户写下的意图；不能为了简化或解决冲突而静默删除。
- 不默认要求 TDD、正式计划、工作树或子代理；仅在好档中风险确实高、或用户明确要求时单独采用。
- 遇到会改变行为的冲突时，指出具体冲突并等待用户决定；不要替用户删需求。
- 修改范围与用户授权保持一致，不顺手重构无关代码。

**所有档都必须做一次与交付形态相符的实际使用检查**——这是省档也不能省的底线，只跑单测、不跑用户真实入口不算。此外按档追加：

- **省档**：用代表性输入跑通即可，不为测试形式本身搭框架。
- **好档**：数据转换、持久化、迁移、已知回归、边界组合，增加针对性自动化测试；UI 要启动并走通核心用户路径（只检查语法或接口响应不算）；用户要可分发产物，就构建后运行该产物，而不只验证源码模式。
- **公司固件 / 产品代码**：遵守仓库规定的编译、静态检查、单元/集成测试、真机或协议验证及文档一致性检查。无法执行的验证要明确说明，不能把“看起来正确”写成“已完成”。

**结构也要验，不只验行为**（个人脚本和应用，按 §5「低耦合底线」）：

- **所有档 · 拔插自查**：本次动到的每条变化轴，交付前搜一遍调用方里有没有另写的成员名单、`if 成员 in (...)`、`成员 == ...` 这类按名特判；有就是没收好，改完再交。测试、文档、配置、输出里出现成员名不算。
- **好档 · 结构测试**：本次新建或收口了变化轴，就补测试：① 调用方的成员清单和能力确实从注册表派生（往注册表加一个假成员，调用方能看到它）；② 成员各有外部依赖、做了故障隔离的，再模拟一个成员加载失败，确认其余成员和聚合命令照常工作。规矩写在文档里拦不住漂移，测试能拦。

**文档跟着改才算完成**：按 `living-blueprint`「什么时候读、什么时候改」里的三种情形判断这轮该改哪份，该改的没在同一轮里改，就不算完成。Claude Code 和 Codex 都有文档闸兜底：前者由 `hooks/doc_gate.py` 读取本轮成功的 Write / Edit，后者由 `hooks/doc_gate_codex.py` 收集本轮成功的 `apply_patch`，在 Stop 时共用同一份判定。改了 vibe 项目代码而文档缺失或两份都没动，每轮只拦一次；被拦时如实判，纯内部改动就说一句为什么不用记，别为过闸写假条目。Codex 的钩子随插件分发，无需改全局配置，但首次使用或定义变更后须在 Codex 中审阅并信任（CLI 用 `/hooks`）。两端都不识别经 shell / Python 脚本落盘的修改，子代理改动不汇总到主会话；Codex 也不收集其他 MCP 写文件工具。没有触发闸不代表文档已经合格，仍须按上述规则判断。

完成时简洁报告：

1. 交付了什么；
2. 实际验证了什么（含拔插自查结果）；
3. 文档改了什么（微脚本免）；活没做完就收尾时，`HANDOFF.md` 已更新到能让零上下文的接手者直接开工；整件事做完时，`HANDOFF.md` 已删；
4. 哪些高风险项尚未验证。

## 9. 收工之后（只在命中时提一句，不是收尾仪式）

省档做完就结束，什么都不提。好档在命中下列情形时，**用一句话告诉用户有这个动作可用**，用户要才做：

| 命中情形 | 可用动作 |
|---|---|
| 迭代多轮、开始觉得“这块是不是不用做” | `cut-scope` 剪枝（只读，只给方向） |
| 做到能用了，想知道生态位和能抄的点 | `scan-field` 的**回头那头**（产原创度对比 + 升级方向文档） |
| 这轮做的正好是 skill / 插件本身 | `skill-review` 复盘（在 xu-skills 插件） |
