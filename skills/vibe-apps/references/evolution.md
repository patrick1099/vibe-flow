# 应用演进：换路线、框架、语言或网站交付

只在实际要迁移或改变交付方式时读。普通功能修改沿用当前实现；“以后可能”不要求提前迁移、预建桥接或维持两套应用。

## 迁移前先固定契约

核对当前蓝图、已谈定事项与实际实现：保留协议字节、单位和精度、输入输出、错误含义、数据库/文件格式及可见行为。以代表性输入和期望结果建立迁移验收；用户已有行为不因换栈静默删改。

业务规则与 UI/IO 分离能缩小影响范围，但不保证 core 不动或迁移便宜。先检查框架类型、状态管理与适配器依赖，再判断哪些可复用、哪些要重写。

## 按变化边界核对

- **同语言换 GUI 或 Web 框架**：独立规则可能复用，界面、任务生命周期与适配代码按实际耦合改写；FastAPI 换 Django 也要核对路由、认证、存储和接口行为，不承诺只是换壳。
- **原生与 Web 互换**：重做交互与通信边界。原生可直接调用/发事件，Web 用接口；仅为迁移而给原生补本地 HTTP 没有必要。设备访问、浏览器权限和分发依赖要分别验证。
- **Python 改纯 Rust**：允许明确选择这条路线。实现需要重写；复用语言无关的样例、期望结果、协议/数据/行为和验收契约，Python 源码与测试源码不保证可直接复用。独立验证工具使用 Python 不影响交付应用的纯 Rust 约束。只有明确需要混合运行时才考虑 FFI/PyO3，不作为迁移必经步骤。
- **桌面变多人网站**：确认浏览器/服务器交付需求后选 Web，核对数据与设备归属、认证、并发、存储隔离和错误处理。参数显式的规则更易复用，但原本桌面的应用状态和 IO 不能直接假定适合多人使用；按当前需求实现，不提前建登录。

## 验收

在目标平台运行实际交付产物，验证已固定的行为与数据契约；有资源目标时做同机、同负载的前后比较，记录构建/库版本、进程范围及采样条件。模拟、源码测试、打包运行和真机验收分开报告，不把某种语言或一次短测当作达标保证。
