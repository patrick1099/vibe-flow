# 应用分层与展示状态

本文件分两部分：Clean 分层是可选的应用架构契约，管业务、用例、IO 的分层与依赖方向；展示状态规则对所有 GUI 应用适用，管界面这一层的状态归谁、怎么更新。两者分开选，不是套餐。新项目先按 `vibe-flow` §4 讨论；展示状态的核心几条另在 [vibe-apps 共用边界](../SKILL.md#架构讨论与共用边界) 摘要，改动涉及展示状态或后台结果时读本文件对应小节。

0.24.0–0.26.0 本文件叫「Clean Architecture + MVVM」。既有项目里叫 ViewModel 的模块按本文「展示状态」理解，不为新规范改名或删除；新代码不再用 ViewModel、Presenter 这类名字。用户 2026-10-28 定：MVVM 的收益大半来自框架自带的数据绑定，在 Tk、原生 JS 这类没有对象级绑定的框架里硬做，会多出一层手写同步、同一字段存两份。

## 适用与迁移

- Clean 分层：有业务规则、用例编排、设备或任务生命周期的应用重点考虑；简单界面可以只分开界面与纯逻辑。CLI、一次性脚本没有 GUI，不套展示状态规则，业务分层按项目规模另定；公司固件照各自项目规范；纯静态页面不造空层。语言、框架、交付路线仍按共用入口选择。
- 既有项目普通修改沿用已定架构，包括 0.24.0 之后按 Clean + MVVM 起的项目，不因修 bug 或新规范自动迁移。明确迁移时先列职责、模块与需要禁止的依赖边，固定现有行为/数据契约；本次未迁移的边界建立精确基线，不用整目录忽略放行新增越界。
- 迁移范围超出授权时，说明完成这条职责链需要改哪些地方，由用户决定。用户选择暂不迁移就保持现有行为，说明仍未迁移的边界，不报告成已符合；局部迁移只报告局部符合。

## 职责和状态所有者

| 职责 | 持有与执行 | 不应承担 |
|---|---|---|
| domain | 领域数据、业务不变量、纯规则 | GUI、网络、设备、数据库、配置文件读写 |
| application | 用例、会话/任务、恢复与退出清理；定义外部依赖 ports | 控件/窗口、具体驱动/数据库、界面刷新 |
| 展示状态 | 影响界面判断的状态、跨事件的请求代次/在途标记、结果与错误到显示的映射 | 实际 IO、业务流程与资源的最终所有权 |
| View | 控件/DOM、布局、框架绑定、事件回调、框架线程调度 | 业务判断、设备生命周期 |
| infrastructure/adapters | 实现 ports，封装驱动、存储、网络、系统调用 | 决定上层业务策略、反向更新窗口 |
| composition root | 读取配置、构造并注入依赖、连接事件、启动/停止入口 | 在入口重写业务工作流 |

业务状态只认 application/domain 的权威来源，展示状态里的 busy、选择项、错误文字是投影，不成为第二个业务状态源。不能只靠按钮置灰保证业务互斥，业务执行条件由内层校验。

## 允许的源码依赖

- domain/application 不导入外层：GUI 框架、具体设备驱动、数据库实现，以及本项目的展示层和 adapters 模块。它们可以定义并使用自己的 ports。合法的内层类型 re-export 可以使用；不能借 re-export、全局 service locator、任意回调或 `Any` 偷渡窗口/数据库/驱动句柄。跨界传普通数据、结果和明确契约。
- application 依赖自己或 domain 定义的 port；infrastructure 依赖并实现该 port，入口注入。运行时调用会执行 adapter，不代表内层可以源码依赖具体 adapter。
- 展示层可以导入所选 GUI 框架，判据是需要验证的逻辑能不能不开窗口测试（例如实现框架 Model 接口、带无窗口测试的列表模型可以）；但它不取得设备和业务任务的最终所有权。
- 一个真实 IO 实现也需要窄 port，可用 Protocol、trait 或签名明确的函数。只声明实际操作，不为分层建通用 Repository、DI 容器或事件总线。测试替身不算第二个产品成员。
- 有具体 IO/工厂的注册表留在外层，通过入口注入的 catalog port/普通元数据/工厂契约使用；界面经 application 查询，不导入 adapters 注册表。纯规则注册表可留在 domain。
- 小应用可用几个文件，不要求多 crate/package；无领域规则不造空 domain。存在用例编排就独立于界面回调，不能以体量小为由塞回 View。

## 展示状态

展示层按单向数据流理解：**状态**（影响界面判断的值）→ **apply(state, event)**（需要进状态的输入事件、用例结果、后台结果经它进入）→ **render**（状态到界面的投影）。这是职责分工，不是脚手架清单：不要求每个页面建三个模块；简单字段和局部草稿由框架绑定直接同步，不经 apply；render 可以完全由框架绑定承担。

- **业务判断不写在控件回调里**。回调只取输入、提交意图（可直接调用 application 用例，Web 经 client）、交回结果；耗时工作交后台，回调不阻塞。任务编排、资源生命周期仍归 application。
- **每项状态一个权威来源，不逐控件镜像**。简单的局部编辑草稿由控件或它绑定的变量（Tk Variable、Slint `<=>` 属性、DOM value）持有，提交时读取，render 不覆盖未提交的内容；参与跨控件联动、异步预演、跨视图共享或多步流程的草稿，归明确的展示状态，由输入事件更新，不能两边各改各的。
- **优先用框架自带绑定**。框架支持的纯展示派生（文字、显隐、颜色、按钮可用性）写在绑定里定义一次；绑定不了的派生，以及没有绑定的框架（原生 JS），集中在一个 render/刷新函数里定义一次，可以增量更新。业务执行条件不放在这两处。
- **按本次改动抽取，不预建**。只看本次新增或修改的代码：同一换算第二次出现 → 抽成共用纯函数；回调里出现请求序号比对、在途请求标记、晚到丢弃，或多步对话框流程 → 把这些转换集中到一处状态转换逻辑，已有就复用，并测它的事件序列。回调区分有限的动作集用枚举，不用字符串前缀；会重排或刷新的列表传稳定 id，不传下标。
- **不造框架**：不建 BaseViewModel、通用绑定框架、Store/Dispatcher、中间件、Redux 式状态库或自研虚拟 DOM。

## 后台任务与生命周期

原生应用默认由 **UI 线程独占可变的展示状态**。后台 application/adapter 仅产生普通结果事件，放入有界通道；View 在 UI 线程调度消费，需要进展示状态的经 apply 更新，再由绑定或刷新函数更新控件。后台不直接改展示状态或控件。无需后台工作时不造线程/队列；不默认用锁包住整份状态。

application 管任务标识、启动、取消、互斥和资源清理；adapter 管具体资源。过期会话、取消后结果按契约丢弃或记录，不能覆盖新会话。分工上：会话和任务是否仍有效由 application 判断，请求与回复的对应由 client 或 adapter 处理；界面这边只负责「旧结果不覆盖当前显示」，这个判断放在 apply 一处，便于测试。大日志用增量/窗口/限量快照，不每帧复制完整历史；小状态可用完整快照。

关窗后继续运行和真正退出是不同意图。继续运行由独立的内核进程承担：关闭界面只保存展示状态、退订并退出界面进程，不取消业务、不释放设备，也不靠隐藏窗口或托盘留住界面（见 [gui-lifecycle.md](gui-lifecycle.md)）。下面的真正退出在单进程应用里就是关窗，拆进程后只用于内核的整体停止。真正退出只有一个幂等用例：View 拦截关闭，界面显示退出进度，后台停止接收新任务、结束/取消工作、释放资源；完成或按约定处理超时/失败后，View 解除订阅、撤销调度并销毁窗口。UI 不阻塞 join；重复点击和 composition 兜底复用同一退出状态，不另写一套清理。窗口销毁后不再投递展示更新。

例如串口应用：用例结束转发、释放占用，经虚拟口 port 清理本程序拥有的口并保存恢复配置；Windows/com0com adapter 执行操作。归属判定、顺序、失败是否允许退出是明确的业务契约，不放在按钮回调里。

## 框架映射

- **ttk**：`core.py / application.py / ui.py / adapters.py / app.py` 按需存在；满足上面抽取条件才加 `state.py`（状态 + apply 纯函数）。Tk Variable 承担简单字段的双向同步，after 在 UI 线程消费后台事件、调 apply、再刷新受影响的控件。
- **Rust/Slint**：`.slint` 的属性、global 与回调就是展示状态和事件接口，简单派生写在绑定里，Rust 侧不镜像一份再逐字段推回属性。Rust 按功能分模块，只放请求代次、在途标记这类记账状态和纯转换函数；大列表用自定义 `slint::Model`。`lib.rs` 导出可测试的模块，`main.rs` 组装；单 crate 的模块拆分不是完整的编译依赖闸。
- **Web**：DOM 事件处理 → 注入的 client（实现 HTTP）→ 服务器 API（入站适配器）→ application → domain/ports。前端需要跨事件状态时，状态与 apply 写成不依赖 DOM/fetch 的 ES module，render 写 DOM；后端不依赖前端模块，业务规则由服务器权威校验。无需引入新前端框架。
- **拆了内核进程的应用**（见 [gui-lifecycle.md](gui-lifecycle.md)）：业务分层默认集中在内核；界面进程默认只有展示层和连内核的 client，界面确有独立的本地用例或 IO 时仍按职责分开。重连、重同步、分页、请求与回复的对应归 client，client 不导入 GUI。
- 其他已选框架映射实际职责，不为迁就模板换框架。

## 验证要求

验证按本次规模与已选架构执行，不把每次小改升级成测试框架建设：

- **既有小改**：复用已有检查，跑代表性行为或必要的针对性测试；不因改文案、样式或单个行为新建检查器、夹具体系和全套分层测试。
- **新项目或明确的边界迁移**：落实下面适用的检查，写进常规测试/CI；实际命令、覆盖范围和未覆盖部分写入 AGENTS，执行后报告结果。

1. **依赖检查（默认轻量）**：一条禁止导入测试，断言 domain/application 不导入 GUI 框架、具体设备驱动、数据库实现，以及本项目的展示层和 adapters 模块；内层自己的 ports 不拦。Python 用标准库 `ast` 解析导入，不用正则；测试同时断言扫到的文件数大于 0，防止路径写错时空跑通过。它是拦截手段，只拦列明的导入形式，通过不代表架构合规；间接依赖、动态加载、宏等未覆盖部分如实写明。已有更强的检查照常保留。
2. **升级条件**：只有人工发现一次真实越界、而现有检查漏报（包括经 re-export 或动态导入绕过）时，才评估加强检查，优先复用现有工具；被现有测试拦住不算。用户 2026-10-28 定为放轻，复议条件即此条。
3. **展示状态**：命中抽取条件的状态转换，用生产代码里的那一处逻辑测事件序列，按涉及的功能覆盖乱序返回、取消后的结果、切换选择和错误恢复；不开窗口，不接真实 IO。几个格式化函数的测试不能代替它。
4. **用例行为**：假 port 验证相关业务顺序、失败与副作用；纯规则测输入输出，不只验证 mock 被调用。Web 前端测试工具与运行依赖分开，具体做法见 Web 分支。
5. **真实界面与设备**：绑定、线程调度、输入、退出及交付产物仍按分支在真实窗口验证。上述自动检查不证明 GUI 或真机通过。

本技能给的是项目验证契约，不是已经替所有应用安装的架构闸。
