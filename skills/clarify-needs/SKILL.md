# clarify-needs：把真需求挖出来，别被方案和偏好带跑

## 总纲

vibe coder 抛来的"需求"，常把**目标、方案、偏好、约束混在一层**。你的活是把它们分开、挖到朴素诉求，落一张轻清单 `docs/NEEDS.md`；回头时拿这张清单对现实。

**这个"混"不是均匀的，是一条有方向的失衡——手段说太死，目标说太空。** 两头各有各的坏法：

| 说得太死 | 说得太空 |
|---|---|
| "用爬虫抓下来存 Excel"、"最好别用 X" | "要简单、好看、稳定" |
| 你会照着做，**该换更好的路子也不换** | 你只能按行业最佳实践**瞎猜**，猜出来的未必是他要的 |
| → 把它松开：确认是真约束还是可替换的手段 | → 把它钉实：翻成看得见的标准 |

所以澄清不是"多问几句"，是**朝两个相反方向各扳一下**。这条轴直接对应下面三步的存在理由：挖目标（治空）、偏好 vs 约束（治死）、验收翻译（治空）。

**一进门先分岔**：用户此刻在**开口**（刚要做东西 → 挖需求）还是**回头**（东西做了一阵 → 拿清单盘点）？

**给用户的出口永远是大白话。** 下面这些角色/档位/透镜都是**你脑子里的工具**，别甩给用户。

## 何时用 / 不用

- **用**：请求里方案/偏好/约束混着目标；需求越聊越多；分不清某条是目标还是手段；用户给了技术方案但没说为什么；回头想知道"这项目做到哪了"。
- **微任务（跑完即弃的微脚本、一句话能干完的小活）**：默认不必触发本 skill；若用户已手动 `/clarify-needs`，也**只锚一句真需求就开干**，别起全套（起了就是过度工程）。

---

## 开口那头：先挖需求

**1. 挖目标（最关键，别跳）。** 用户给的往往是方案（"用爬虫抓下来存 Excel"）。**先判断目标清不清楚**：

- **目标缺失**（只有方案、没说为什么）→ 钻实现细节之前，先回问一句"你拿这东西最终想达成什么 / 想省掉什么？"
- **目标已说清**（用户已经讲了场景+痛点，如"每周手动抄两小时、经常抄错"）→ **直接锚定，别重复追问 why**，进入范围和验收。

> ❌ 目标没挖到就直接问"抓哪些页面/什么字段/输出格式" → 你在帮他把方案做细，没碰真需求。
> ✅ "你要这批数据做什么用？" → "我每周手动抄这些，烦，想省这个力。"（**这才是需求**）

**2. 轻查偏好 vs 约束。** 遇到"最好别用 X""越小越好""必须用 Y"，追一句：**这是硬性上限/环境强制（有明确来源和违反后果），还是你的偏好？** 硬约束保留；偏好留到方案比较那步，别让它径直主导架构。

> "我听说 Electron 重，别用" → 追问："是有体积/设备上限，还是听说而已？" 没上限就是偏好。

**3. 轻查验收。** 遇到"简单/好看/稳定/好用"，翻成**最少几条能看见的标准**（字号多大？几步记完一笔？断电丢不丢数据？）。别原样复述当分析完，也别脑补整套无障碍体系。

**4. 锚一句真需求**（挖到就落一句，不含可替换手段）：

> 在【场景】下，【谁】想从【现状】变成【目标状态】，为了【朴素价值】。

**协议 / 运行环境 / 合规**（Modbus、必须离线、Win7）**不是手段，是约束，不许当技术词剥掉。**

## 回头那头：按需求盘点（写薄）

1. **有 `docs/NEEDS.md`** → 逐条对现实，大白话讲每条做了 / 没做 / 做一半。
2. **诚实边界**：**没有实际运行证据（没跑过、没测过、没打开看过）就不说"做好了/达标"**，改说 **"看起来写了，但我没替你实际试过"**。回头**只讲需求**，别掺代码质量挑刺（那是另一回事）。
3. **找不到 NEEDS.md** → 先从对话、现有文档、用户陈述**重建需求**，把重建出的清单**摆给用户确认**，再盘。**绝不退回"按功能盘点（能用的 / 空壳）"**——那是旧 reality-check 的废做法。

---

## 缩放闸

需求分析在对话里推理、便宜。但**微任务默认不必触发本 skill；若已手动触发，只锚一句真需求就开干**，不起全套、不生成 NEEDS.md、**永不进厚版**。给微任务硬套整套归位分级 = 过度工程。

## 给用户永远大白话

判据：**这段能不能念给不懂代码的人听？** 术语、架构名、"核心/底线/可换可降"这些档位名一律翻译掉，一屏封顶。给用户大致这几句：

- 我理解你真正要解决的是……
- 第一版必须做到……
- 你提到的这些做法可以换，技术方案留到下一步探方案……
- 这些可以换做法 / 暂时不做……
- 如果超出你的投入，我会先从这里砍……

## NEEDS.md（轻，两区，不是 11 节模板）

- **当前需求区**：项目当下有效的需求。写**真需求锚**一句，然后把需求分**四组**（大白话，别写内部档位名）：
  - **第一版非做不可** / **必须达到的及格线** / **做法可以替换** / **这一版先不做**。

  （想要更细的归位与劝退，才按 SKILL 末尾「何时拉厚版」进 `references/`；一般单目标项目，这四组就够落盘。）用户明确取消/替换需求后**允许覆盖更新**（否则回头会把废需求当缺口）。
- **回看记录（可选）**：如需落一次回头结果，按日期追加、不改历史。默认回头结果**只在对话说，不强制落盘**。

## 何时拉厚版（`references/deep-needs-analysis.md`）

**先过缩放闸——微任务一律不进厚版。** 在此前提下，出现任一即读厚版走完整 5 角色 / 分级 / 劝退：

- 用户明说"深挖 / 严格分析 / 完整归位"。
- 你**写不出**一句不含可替换手段的真需求锚。
- 出现**两个以上**独立用户或独立目标。
- 需求明显**装不进**用户的时间/精力上限。
- 分不清某条是**手段 / 偏好 / 硬约束**。
- 你对**怎么分级**没把握。

> **诚实标注**：厚版是**跨模型兼容兜底**，没有被实测证明为默认必需（多数情况你不拉它也做得对）。它**降低而非消除**风险——"何时进厚版"本身也要判断力。这是兜底，不是保证。

## 与邻居划界

| 对象 | 它是什么 | clarify-needs 的不同 |
|---|---|---|
| 探方案（`vibe-flow` §4；要重仪式则 `superpowers-manual` 的 brainstorming） | 需求明确后探索方案、比取舍、要用户确认 | 它的**可选前置**；不替用户拍方案，也不剥夺其批准权 |
| cut-scope | 事后、只读，砍已迭代多轮的**设计** | 开口就介入，挖**需求**、防膨胀 |
| living-blueprint | 机器读的"现在是什么" | 人读的"你的哪些需求做了/没做" |
| reality-check（旧） | 回头按**功能**盘点能干啥 | 回头按**需求**盘点（功能盘点已废） |

## 反模式

- 需求还没厘清就逼用户拍技术方案；或反过来剥夺用户对方案的批准权。
- 把用户嘴上的需求 / 顺手给的方案当真需求，照单全收。
- 手段冒充目标、偏好冒充约束没识别就往下做。
- 用术语/架构名/档位名跟用户讲（听不懂 = 白讲）。
- 没跑过说成"做好了"；回头掺代码质量挑刺。
- 给跑完即弃的微脚本硬套整套归位分级，或让它进厚版。
- 偷偷删核心目标/最低验收，假装项目做完了。
