# brainstorm：多 agent 头脑风暴（只在你叫的时候跑）

## 总纲

> 平时的外援是「主 agent 先出方案、决策者挑毛病」（[collaboration.md](../vibe-flow/references/collaboration.md)），它会锚定：审的人只围着给定方案改，不会说「整条路换掉」。头脑风暴在方案还没出来时先发散、再收敛。

主 agent 在这里只当**主持**：出简报、派视角、匿名、转运材料。**不出方案、不表态**，转交时也不加自己的倾向。推荐由主席给，拍板归用户。

只用于个人项目；公司固件 / 产品代码不适用，被叫到那里就直说。

## 先过一道：这步值不值得讨论（只提醒一次）

**同时满足**下面两条，才说一句「这步不用讨论，审一下就行」，并指向 collaboration.md 的方案审或结果审：

- 没有需要重开的路线问题；
- 眼下只需要按既定标准审查或执行（例如代码已写完只差审查）。

只提醒一次。用户坚持就照跑，不要求他证明价值。**不以「项目小」「代码已写完」单独作为劝退理由。**

## 席位

只让提案席按已确认方式并行；主席在提案及必要交锋结束后启动，配置中的 parallel 不表示主席同时开工。

席位、主席、模型、思考程度、调用工具与串行/并行方式从 [协作配置](../vibe-flow/references/collaboration-config.md) 给出建议，主持集中请用户确认后写入本次执行约定。用户已指定或授权沿用的部分不重复问；主流程不固定席数、厂商或模型。

- 主持只转运材料，不参与提案；主席必须另开新会话，不能复用任何席位的提案会话。
- 全部参与者只读，工作目录为项目根；按工具/后端实际权限设置并验证，不把文字只读当沙箱。
- 每席独立收到完整简报与视角，不能读其他席的提案；材料以所选工具支持的直接文本、stdin 或文件传入，并验证读取的是明文。
- 配置建议只定义组合，不代表已安装、认证或模型设置可用；调用前检查能力和接受回执，失败时不静默换席。

## 流程

**0. 运行目录。** `<项目根>/.vibe-flow/brainstorm/<YYYYMMDD-题目>/`。简报、各轮原文、匿名映射、纪要都由主持写在这里；席位只读，不写答卷。运行目录由主持创建 `.gitignore`（内容 `*`），不依赖派工工具自动忽略。旧运行目录保留，不迁移或删除。另记一份 `run.md`：用户确认的配置快照、每席的模型/思考程度/权限、实际命令、轮次、原生会话 ID、状态和匿名映射；恢复使用此处快照而非最新默认。

**1. 简报（`brief.md`）。** 不写任何方案或倾向，免得锚定。

- 题目一句话；用户要的可见结果。
- 条件分三栏：**硬约束** / **偏好** / **可重议的假设**。来源是 HANDOFF「已谈定」、`NEEDS.md` 和对话；已谈定的结论不自动都是硬约束，过去的技术假设放第三栏。
- 验收：怎样算好方案。
- 相关文件的精确路径。

**2. 派视角（写进 `run.md`）。** 视角不固定，从这道题的真实矛盾里找。每席三行：

```
题目条件：……（这道题里让这个视角成立的事实）
优先检验的取舍：……
推翻条件：出现什么就放弃这个方向
```

- 主要的对立两极：分给不同席；有多种模型可用时优先避免同一模型同时演正反两极。
- 其余席探**不同维度**，不是同一条轴上的中间值；只分人设名容易换措辞不换路线。
- 可以让一席质疑「到底需不需要新建 / 改」，在硬约束之内。
- 不指定具体方案，不为凑分歧硬造对立。

**3. 第 1 轮：盲出方案（按已确认组织方式）。** 每席收到：简报全文 + 本席视角 + 下面的格式。正文 ≤800 字，证据 ≤5 条，可以短写。原文存 `r1-<席位>.md`。

```
## 方案（一句话）
## 怎么做
## 假设（每条标 FACT / INFERENCE / ASSUMPTION / UNKNOWN；FACT 附 file:line 或来源）
## 代价
## 反证：什么情况说明这条路错了
```

**4. 匿名。** 去掉席位和模型身份，按实际席数标成匿名代号；**每给一位读者都重新打乱顺序**，映射只记在 `run.md`。不改写方案文字，免得主持的转述成了新的过滤。

**5. 第 2 轮：交锋（按需，默认不跑）。** 只有出现「会改变路线、且能靠交锋澄清」的分歧才跑。缺代码事实就由主持查证或标未知，缺用户偏好就留给用户拍板，这两种都不靠交锋补。

跑的时候：挑持对立意见的两个席，**各开新会话**（不续用第 1 轮的会话，否则它知道哪份是自己的、会转去防守）。给简报 + 匿名各案 + 要回应的那个分歧；每案意见 ≤120 字，允许写「无异议」但要给依据。原文存 `r2-*.md`。

**6. 主席。** 独立的新主席会话，输入简报 + 匿名各案 + 交锋意见（有的话）。纪要 ≤800 字，存 `chair.md`：

```
## 未解决的分歧（写在最前）
## 共识
## 推荐方案与理由
## 为什么没采纳最强的那条反对意见
## 少数派意见（保留，不抹平）
## 什么情况说明推荐错了
## 下一步（一个具体动作）
## 需要用户拍板的点（翻译成用户感知得到的后果）
```

要求：重复的论据合并，**几席说同一句不算多票**，不按票数收敛；关键结论保留 FACT / ASSUMPTION 标签。

**7. 交给用户。** 主持原样转交主席纪要，附：各案一句话摘要（此时可揭示哪份出自哪席）、缺席情况、实际调用次数。主持不加自己的倾向。用户拍板。

**8. 记下来。** 用户拍板后，按 [vibe-flow §4](../vibe-flow/SKILL.md) 在 HANDOFF「已谈定」记一条，来源写「头脑风暴采纳（运行目录名）」。这个方案**不再**走 collaboration.md 的方案审，免得同一件事买两遍。不另建文档，运行目录留在本地供回看。

## 预算与失败

- **调用次数**：按确认的席数加一个主席计算；跑交锋再加两次。并行省的是时间，不是钱；限篇幅只限输出文字，不限思考消耗。
- **截止**：执行约定明确本轮预算。超时后先查对应命名会话/原生 ID 的状态与结果，只按原约定最多续接一次；不要选“最近一个”或重发。还不回就按缺席收口。恢复后重新核验模型、effort、权限和会话身份，设置丢失就停该席。
- **缺席 / 失败 / 空输出**：纪要里写明「S2 缺席（超时）」，不当成同意。有效方案少于 2 份就停下告诉用户，不出推荐。

## 反模式

- 主持写自己的方案，或转交纪要时加倾向
- 自己触发本 skill，或以「项目小」为由劝退
- 把「已谈定」全部当硬约束塞进简报
- 每次套同一组固定视角；多个席只给人设名
- 默认跑交锋；交锋续用第 1 轮会话
- 主席沿用任一席位的会话；按票数收敛；多席说了同一句就算多票
- 把缺席或空输出当同意
- 头脑风暴之后再把同一方案送决策者审
