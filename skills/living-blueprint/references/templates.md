# 四份文档的模板

建文件、或要调整某份文件的结构时才读本文件。每份写什么、什么时候更新，规矩在 `living-blueprint` 的 SKILL.md；哪些项目要哪些文件，见 `vibe-flow` §6。

用不上的节、行直接删掉，不为形式填满，也不写「无」。唯一例外是 CHANGELOG 的「没选的路」，必填。

## BLUEPRINT.md

```markdown
# <工具名> 蓝图
> 活蓝图：正文永远是当前真相，改了就覆盖。只讲功能不讲实现。
> 重构照本文行为契约重写即可；未列为硬约束的一切都是实现细节，可自由更改。

## 1. 一句话
这工具是什么、给谁、解决什么。

## 2. 功能与行为 + I/O 契约
逐个功能写成「给它什么 → 它做什么 / 用户看到什么」（可观察行为，不写内部怎么算）。
- <功能A>：给 <输入/操作> → <输出/可见行为>
- <功能B>：给 … → …

**I/O / 数据契约（换语言必须逐字保留）**：输入格式、输出格式、持久化/文件格式、对外接口的字段。写清字段/列/结构约定，不写内部数据结构与算法。
- <输入>：<格式/字段/来源>
- <输出>：<格式/字段/去向>
- <持久化/接口>：<文件格式 / API 字段 …>

## 3. 边界 / 明确不做
故意不做的事，防重构时功能膨胀。

## 4. 硬约束 + 重构自由声明
- 运行约束：如 离线运行 / 单文件 / 必须吃某格式 …
- 可移植架构约束：换语言仍成立的原则，如 逻辑与 UI/框架解耦、逻辑层可独立测试、通信走标准协议不用专有桥。
- 变化轴：「加或去掉一个 <成员>，只动它自己的适配器和注册表。」成员各有外部依赖、做了故障隔离的，再加「一个 <成员> 出错只影响它自己」。
- **以上未列出的一切均为实现细节，重构可随意更改。**

## 5. 功能痛点 / 易错点
这个功能为什么难做对、容易错在哪。是第 2 节的补充，不是代码 bug 库。
```

## CHANGELOG.md 的一条

新条目插在文件**顶部**。

```markdown
## 2026-09-23 <一句话：变了什么>

**起因**：用户看到了什么 / 碰到了什么、怎么发现的。能引用户原话就直接引。
**根因**：（bug 类必填）为什么会这样。体验类写「哪里别扭、为什么别扭」。
**改成**：现在的可观察行为。
**没选的路**：考虑过但否掉的方案，和否掉的理由。没有就写「无」，这一行不许省。
**影响**：用户要不要做什么、旧数据 / 旧配置还能不能用。（没有就省略这行）
```

## AGENTS.md

放项目根，一屏以内。

```markdown
# <项目名>

## 先读
1. docs/HANDOFF.md —— 现在做到哪了（没有这个文件 = 没有进行中的工作）
2. docs/BLUEPRINT.md —— 它是什么、行为契约
3. docs/CHANGELOG.md —— 最近 5 条；要改哪块，再搜那块相关的「没选的路」

## 命令
- 跑：<一条命令>
- 测：<一条命令>
- 打包：<一条命令>

## 代码地图（改哪类东西去哪）
| 要改的 | 去哪 |
|---|---|
| <加一个 X> | <文件 / 注册表位置> |

## 坑
- <这个项目特有、不写就会踩的：编码、写文件的方式、环境变量、平台差异……>
```

分支 skill 自带的架构约束段（如 `vibe-apps` 那段）接在后面。

## HANDOFF.md

放 `docs/HANDOFF.md`（和别的脚本共处一个目录的，用旁挂 `<脚本名>.HANDOFF.md`）。一屏以内。

```markdown
# 交接 · <日期>

**在做**：<一句话：手上这件事是什么、为什么做>
**已完成**：<只列指向 CHANGELOG 的条目标题，不重复内容>
**做了一半**：<哪些、卡在哪、当前是什么状态（未提交？分支？临时文件在哪？）>
**下一步**：<接手的人第一件该做的事，具体到能直接开工>
**等用户拍板**：<没定的问题，和各选项>
**别碰**：<暂时不能动的东西和原因>
```
